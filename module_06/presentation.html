Ожидаемые ответы: JOIN здесь не нужен — события не связаны «один к одному», JOIN даст декартово произведение по датам/линиям. Нужно поставить наборы друг под другом (UNION ALL), приведя столбцы к общей структуре: тип события, дата, линия, количество, единица, сумма; там, где значения нет, — NULL. 01

Действия с наборами. UNION и UNION ALL

JOIN соединяет строки «по горизонтали», операции над наборами — «по вертикали»

Операции над множествами

UNION

строки из A или B

INTERSECT

строки, которые есть и в A, и в B

EXCEPT

строки из A, которых нет в B

Сравниваются строки целикомДве строки «равны», если равны все столбцы по позициям; NULL при этом считается равным NULL (как в DISTINCT).

Требования к совместимости наборов

  1. одинаковое число столбцов во всех ветках
  2. совместимые типы по позициям (integer + numeric — да; integer + date — нет)
  3. имена столбцов результата берутся из первого запроса
  4. ORDER BY и LIMIT — один раз, в конце; для ветки — только в скобках
Решение для типовЯвное приведение: customer_id::text, 'Брак'::text, NULL::numeric.

-- ОЖИДАЕМАЯ ОШИБКА
SELECT customer_id, customer_name FROM customers
UNION
SELECT supplier_id FROM suppliers;
-- each UNION query must have the same number of columns

-- ОЖИДАЕМАЯ ОШИБКА
SELECT customer_id       FROM customers
UNION
SELECT registration_date FROM customers;
-- UNION types integer and date cannot be matched

-- Правильно: ORDER BY + LIMIT у ветки — в скобках
(SELECT customer_name AS name FROM customers
 ORDER BY customer_name LIMIT 3)
UNION ALL
(SELECT supplier_name FROM suppliers
 ORDER BY supplier_name LIMIT 3);

Квиз: имена и порядок

Как будет называться второй столбец результата и можно ли отсортировать по нему?


SELECT 'Клиент'    AS contact_type, customer_name AS name, phone FROM customers
UNION ALL
SELECT 'Поставщик',                 supplier_name,         phone FROM suppliers
ORDER  BY ???;
  • customer_name; сортировать можно только по номеру столбца
  • supplier_name — берётся из последнего запроса
  • name; можно ORDER BY name или ORDER BY 2
  • Столбец не получит имени, сортировать нельзя

Имена результата задаёт первый запрос. ORDER BY в конце применяется ко всему объединённому набору и видит эти имена (или позиции).

Все результаты проверены на БД. T-SQL поддерживает только INTERSECT / EXCEPT без ALL; PostgreSQL — оба варианта.

NULL в наборах: EXCEPT против NOT IN

Задача: найти продукты без возвратов. В журнале возвратов одна строка с неизвестным продуктом (NULL). Сколько строк вернёт каждый запрос?

① NOT IN


SELECT product_id
FROM   (VALUES (1), (2), (3)) AS p(product_id)
WHERE  product_id NOT IN (
         SELECT product_id
         FROM   (VALUES (2), (NULL)) AS r(product_id)
       );
0 строк1 NOT IN (2, NULL) = 1 <> 2 AND 1 <> NULL = TRUE AND UNKNOWN = UNKNOWN. WHERE пропускает только TRUE, поэтому отбрасываются все строки.

② EXCEPT


SELECT product_id
FROM   (VALUES (1), (2), (3)) AS p(product_id)
EXCEPT
SELECT product_id
FROM   (VALUES (2), (NULL)) AS r(product_id);
2 строки: 1, 3Операции над наборами сравнивают строки как IS NOT DISTINCT FROM: NULL не отличается от NULL, и никакого UNKNOWN не возникает.
ПравилоДля «есть в A, нет в B» используйте EXCEPT или NOT EXISTS (тоже вернёт 1, 3). NOT IN — только если подзапрос гарантированно без NULL.
Сначала дать 30 секунд на прогноз и голосование руками: «Кто считает, что ① вернёт 2 строки? 0? 3?». Большинство ответит «1 и 3» для обоих. Затем открыть ответы. Связать с модулем про трёхзначную логику: NULL в сравнении даёт UNKNOWN, но операции над наборами — особый случай, там строки сравниваются «на неразличимость». Практический смысл: один битый NULL в справочнике возвратов обнуляет отчёт, и ошибку никто не замечает — пустой результат выглядит как «возвратов нет». Результаты проверены на БД.

Квиз: EXCEPT ALL на реальных данных

В returns 308 строк, из них 206 — с причиной «Истёк срок годности». Сколько строк вернёт запрос?


SELECT product_id FROM returns
EXCEPT ALL
SELECT product_id FROM returns WHERE reason = 'Истёк срок годности';
  • 0
  • 102
  • 206
  • Столько, сколько различных продуктов без возвратов по сроку

EXCEPT ALL вычитает «экземпляры»: для каждого product_id остаётся m − n строк. В сумме 308 − 206 = 102 (проверено на БД). Обычный EXCEPT вернул бы только продукты, у которых вообще не было возвратов по сроку.

Квиз: приоритет

A = {1, 2}, B = {2}, C = {2}. Что вернёт A EXCEPT B UNION C?

  • {1} — сначала B UNION C, потом вычитание
  • {1, 2} — (A EXCEPT B) UNION C
  • {2}
  • Ошибка: нельзя смешивать EXCEPT и UNION без скобок

UNION и EXCEPT одного приоритета и выполняются слева направо: {1, 2} − {2} = {1}, затем ∪ {2} = {1, 2}. Проверено на БД (examples.sql, 5.3).

03

CROSS APPLY и OUTER APPLY → LATERAL

Подзапрос в FROM, который «видит» строки таблиц слева от него

Зачем нужен LATERAL


-- ОЖИДАЕМАЯ ОШИБКА
SELECT c.customer_name, t.order_number
FROM   customers AS c
CROSS  JOIN (SELECT o.order_number
             FROM   orders o
             WHERE  o.customer_id = c.customer_id
             LIMIT  3) AS t;
-- ERROR: invalid reference to FROM-clause
--        entry for table "c"
-- HINT:  ... you must mark this subquery
--        with LATERAL.

Обычный подзапрос в FROM вычисляется независимо от соседей. LATERAL разрешает ссылаться на таблицы левее — подзапрос выполняется для каждой их строки.

CROSS JOIN LATERAL: 3 крупнейших заказа каждого клиента


SELECT c.customer_name,
       t.order_number,
       t.order_date,
       t.amount
FROM   customers AS c
CROSS  JOIN LATERAL (
         SELECT o.order_number, o.order_date, i.amount
         FROM   orders   AS o
         JOIN   invoices AS i ON i.order_id = o.order_id
         WHERE  o.customer_id = c.customer_id

ORDER  BY c.customer_name, t.amount DESC;

LATERAL с generate_series и unnest


-- массив смен → строки, брак по каждой
SELECT l.line_id,
       sh.shift,
       (SELECT ROUND(100.0 * SUM(b.defect_qty)
                     / SUM(b.produced_qty), 2)
        FROM   production_batches b
        WHERE  b.line_id = l.line_id
          AND  b.shift   = sh.shift) AS defect_pct
FROM   production_lines AS l
CROSS  JOIN LATERAL
       unnest(ARRAY['День', 'Ночь']) AS sh(shift)
ORDER  BY l.line_id, sh.shift;

Линия 3: День 1.62 · Ночь 7.94; у других линий смены одинаковы (1.55–2.34).


-- календарь месяцев + выручка месяца
SELECT to_char(m.month, 'YYYY-MM') AS month,
       r.revenue
FROM   generate_series(DATE '2025-01-01',
                       DATE '2025-12-01',
                       INTERVAL '1 month') AS m(month)
CROSS  JOIN LATERAL (
         SELECT ROUND(SUM(oi.quantity * oi.unit_price
                          * (1 - oi.discount_pct / 100))) AS revenue
         FROM   orders o
         JOIN   order_items oi ON oi.order_id = o.order_id
         WHERE  o.status <> 'Отменён'
           AND  o.order_date >= m.month
           AND  o.order_date <  m.month + INTERVAL '1 month') AS r;
-- 12 строк; минимум 2025-07: 24,7 млн

LATERAL, коррелированный подзапрос или окно?

«Последний заказ каждого клиента» можно получить тремя способами:

  1. коррелированный подзапрос WHERE order_date = (SELECT MAX(...)) (модуль 5);
  2. LEFT JOIN LATERAL (... ORDER BY ... LIMIT 1) ON TRUE;
  3. ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ...) (модуль 8).

Чем они отличаются при «ничьих», при необходимости вернуть 3 строки, при наличии индекса (customer_id, order_date)?

⏱ 5 мин
Ожидаемые ответы: (1) при равных датах — несколько строк, только одна строка «вверх», плохо обобщается на top-N; (2) ровно N строк, детерминированность через доп. ключ сортировки, отлично работает с индексом (customer_id, order_date) — по индексу для каждого клиента читаются N строк; удобно, когда внешних строк мало, а детальных много; (3) один проход по всей таблице, хорошо, когда нужны почти все группы и сравнение внутри окна. Нет единственно правильного — выбор по объёму и индексам.

Что запомнить

  • Наборы совместимы: число столбцов, типы по позициям; имена — из первого запроса; ORDER BY — в конце
  • По умолчанию — UNION ALL; UNION удаляет дубли и может «съесть» данные
  • Столбец-признак источника — обязательный приём для лент событий
  • INTERSECT — сильнее UNION/EXCEPT; при смешении — скобки
  • EXCEPT несимметричен; пустой результат — тоже результат, но его надо проверить
  • CROSS/OUTER APPLY = CROSS JOIN LATERAL / LEFT JOIN LATERAL … ON TRUE
