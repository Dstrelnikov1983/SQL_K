# Модуль 7. Практическая работа «Модификация данных»

> Демонстрация преподавателя + повторение слушателями. Весь код — в файле [`examples.sql`](examples.sql).

| | |
|---|---|
| **Цель** | Научиться безопасно добавлять, изменять, удалять и сливать данные в PostgreSQL: `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `INSERT … ON CONFLICT`, `MERGE`, `RETURNING`, транзакция-«песочница» |
| **Время** | ≈ 40 минут — в составе лекции: каждый блок показывается сразу после теории (см. план в презентации) |
| **Формат** | Преподаватель показывает шаг, слушатели повторяют в своей личной схеме |
| **Результат** | Личная схема `stud_<фамилия>` с копией данных «Питание +», которой вы будете пользоваться в модулях 7, 9–12 |

## Легенда

Аналитики «Питание +» до сих пор только **читали** данные. Теперь им нужно исправлять ошибки учёта,
загружать новый прайс от коммерческой службы и предложения поставщиков, вести собственные таблицы
(стоп-листы, журналы). Любая из этих операций может испортить данные, поэтому начинаем с правил безопасности.

## Подготовка

### Шаг 0. Подключение и личная схема

1. Подключитесь к учебной БД (DBeaver / psql): сервер `<адрес_сервера>`, порт `6432`, база `db1`, SSL `verify-full` + `root.crt`.
2. Придумайте имя схемы: `stud_` + фамилия **латиницей, строчными**: `stud_ivanov`, `stud_petrova`.
3. Выполните (DBeaver: открыть файл, **Alt+X** — «выполнить скрипт»):

```sql
SET course.stud_schema = 'stud_ivanov';          -- ваше имя схемы
-- затем весь файл module_07/scripts/00_personal_schema.sql
```

Вариант для psql (из корня репозитория):

```bash
psql "host=<адрес_сервера> port=6432 dbname=db1 user=<логин> sslmode=verify-full sslrootcert=root.crt" \
     -v stud=stud_ivanov -f module_07/scripts/00_personal_schema_psql.sql
```

**Ожидаемый результат:**

```text
NOTICE:  Готово: схема stud_ivanov, таблиц 23, строк скопировано 65905
 my_schema   | search_path
-------------+------------------------------
 stud_ivanov | stud_ivanov, pitanie, public
```

и список из 23 таблиц (`customers` — 73 строки, `orders` — 4458, `material_consumption` — 24275 …).

Что сделал скрипт:

| Действие | Как |
|---|---|
| структура | `CREATE TABLE stud_x.t (LIKE pitanie.t INCLUDING ALL)` — столбцы, `NOT NULL`, `DEFAULT`, `CHECK`, PK, `UNIQUE`, индексы, комментарии |
| данные | `INSERT INTO stud_x.t SELECT * FROM pitanie.t` |
| внешние ключи | 30 FK восстановлены по образцу `pitanie` (`LIKE` их не копирует!) |
| ключи | PK превращены в `GENERATED BY DEFAULT AS IDENTITY`, счётчик = `MAX(id) + 1` |
| `search_path` | `stud_ivanov, pitanie, public` — **только в текущем сеансе** |

> ⚠️ **В каждом новом подключении / окне редактора** первой командой выполняйте
> `SET search_path TO stud_ivanov, pitanie, public;` и проверяйте `SELECT current_schema();`.
> Если `current_schema()` = `pitanie` — вы изменяете общую схему!

Если схема уже есть, скрипт остановится с ошибкой `Схема stud_ivanov уже существует` — это защита.
Вернуть исходные данные — `01_reset_data.sql` (Шаг 11).

## Шаг 2. INSERT: одна строка, несколько строк, DEFAULT, RETURNING

Создайте демонстрационную таблицу журнала звонков:

```sql
CREATE TABLE m07_call_log (
    call_id     integer      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id integer      NOT NULL REFERENCES customers (customer_id),
    call_date   date         NOT NULL DEFAULT current_date,
    topic       varchar(100) NOT NULL,
    result      varchar(30)  NOT NULL DEFAULT 'Без результата',
    amount_rub  numeric(14,2)
);
```

```sql
-- одна строка, столбцы перечислены явно
INSERT INTO m07_call_log (customer_id, call_date, topic, result)
VALUES (1, DATE '2026-01-12', 'Напоминание о просроченной задолженности', 'Обещан платёж');

-- несколько строк одной командой + DEFAULT
INSERT INTO m07_call_log (customer_id, call_date, topic, result, amount_rub)
VALUES (1,  DATE '2026-01-19', 'Повторное напоминание',      DEFAULT,             NULL),
       (53, DATE '2026-01-19', 'Согласование графика оплат', 'График согласован', 2000000),
       (7,  DEFAULT,           'Предложение по прайсу 2026', 'Ждёт КП',           NULL);

-- RETURNING: получить сгенерированный ключ без отдельного SELECT
INSERT INTO m07_call_log (customer_id, topic)
VALUES (23, 'Обсуждение промо-акции')
RETURNING call_id, call_date, result;
```

**Ожидаемо:** `INSERT 0 1`, `INSERT 0 3`, затем `call_id = 5`, `result = 'Без результата'`, `call_date` — сегодняшняя дата.

## Шаг 3. INSERT … SELECT

Поставим в план обзвона всех клиентов без e-mail:

```sql
INSERT INTO m07_call_log (customer_id, call_date, topic)
SELECT c.customer_id, DATE '2026-01-26', 'Уточнить e-mail для ЭДО'
FROM   customers AS c
WHERE  c.email IS NULL;
```

**Ожидаемо:** `INSERT 0 21`. Порядок и количество столбцов `SELECT` должны совпадать со списком в `INSERT` — по
**позиции**, а не по имени.

## Шаг 4. Генерация ключей: identity, sequence и почему не MAX()+1

```sql
SELECT table_schema, column_name, is_identity, identity_generation
FROM   information_schema.columns
WHERE  table_name = 'customers' AND column_name = 'customer_id';
```

| table_schema | is_identity | identity_generation |
|---|---|---|
| pitanie | NO | |
| stud_ivanov | YES | BY DEFAULT |

1. `GENERATED ALWAYS` запрещает явный ключ: `INSERT INTO m07_call_log (call_id, …) VALUES (1000, …)` →
   `ERROR: cannot insert a non-DEFAULT value into column "call_id"`. Для миграций — `OVERRIDING SYSTEM VALUE`.
2. `CREATE SEQUENCE m07_claim_no_seq;` + `'ПР-2026-' || lpad(nextval('m07_claim_no_seq')::text, 5, '0')` →
   `ПР-2026-00001`, `ПР-2026-00002`, …
3. **Антипаттерн MAX()+1.** Выполните из `examples.sql` блок 2.4: вставка `MAX()+1` даёт id 14, а следующая
   вставка через identity падает: `duplicate key value violates unique constraint "m07_supplier_note_pkey"` —
   счётчик ничего не знает о «ручном» id. Лечение — `setval(pg_get_serial_sequence(...), max(id))`.

**Подумайте:** два менеджера одновременно выполняют `INSERT … SELECT max(id)+1`. Что получится? Почему
последовательность (sequence) от этого защищена, но допускает «дырки» в нумерации?

## Шаг 5. UPDATE: правило «сначала SELECT»

Задача: дописать в комментарий заказа пометку об опоздании отгрузки.

```sql
-- 1) сколько строк изменим?
SELECT count(*) AS will_be_updated
FROM   orders
WHERE  shipped_date > required_date;              -- 984

-- 2) меняем в транзакции
BEGIN;

UPDATE orders
SET    comment = concat_ws('; ', btrim(comment),
                           'Отгрузка с опозданием ' || (shipped_date - required_date) || ' дн.')
WHERE  shipped_date > required_date;              -- UPDATE 984 — совпало

SELECT order_id, comment FROM orders WHERE shipped_date > required_date ORDER BY order_id LIMIT 3;

ROLLBACK;                                         -- эксперимент отменён
```

**Ожидаемо:** `UPDATE 984`, комментарии вида `ПОВТОРНЫЙ ЗАКАЗ; Отгрузка с опозданием 3 дн.`
После `ROLLBACK` изменений нет.

> 💡 `concat_ws` пропускает `NULL` — у заказов без комментария не появится ведущее `; `.
> Выражение `comment || '; ' || …` вернуло бы `NULL` для таких строк.

Блок 3.3: `CASE` внутри `SET` — разные правила для разных групп (`raw_materials.min_stock`), `RETURNING` вернёт 8 строк.

**Типичная ошибка:** `UPDATE products SET base_price = base_price * 1.05;` без `WHERE` → `UPDATE 35`, весь прайс.
Именно поэтому — транзакция.

## Шаг 6. UPDATE … FROM — изменение по данным другой таблицы

Пересчитаем себестоимость масла по рецептуре и средним ценам закупки IV кв. 2025:

```sql
BEGIN;

UPDATE products AS p
SET    standard_cost = round(c.material_cost * 1.15, 2)
FROM  (SELECT r.product_id, sum(r.qty_per_unit * mp.avg_price) AS material_cost
       FROM   recipes AS r
       JOIN  (SELECT poi.material_id, avg(poi.unit_price) AS avg_price
              FROM   purchase_order_items AS poi
              JOIN   purchase_orders      AS po ON po.po_id = poi.po_id
              WHERE  po.order_date >= DATE '2025-10-01'
              GROUP  BY poi.material_id) AS mp ON mp.material_id = r.material_id
       GROUP  BY r.product_id) AS c
WHERE  c.product_id = p.product_id
  AND  p.product_id IN (13, 14)
RETURNING p.product_id, p.base_price, p.standard_cost;

ROLLBACK;
```

**Ожидаемо:**

| product_id | base_price | standard_cost |
|---|---|---|
| 14 | 159.00 | 141.26 |
| 13 | 189.00 | **195.94** |

Даже по «свежему» расчёту масло 82,5 % стоит дороже своей цены.

> ⚠️ В `UPDATE … FROM` условие соединения с целевой таблицей обязательно. Если источник вернёт для одной строки
> цели **несколько** строк, PostgreSQL молча применит одну из них (какую — не определено). Агрегируйте источник!

**RETURNING «старое и новое».** В PG 16 `RETURNING` видит только новую версию строки. Приём из блока 3.6 —
соединить таблицу с самой собой: `UPDATE products AS p … FROM products AS old … RETURNING old.base_price, p.base_price`.

## Шаг 7. DELETE, DELETE … USING, каскад, TRUNCATE

```sql
SELECT count(*) FROM order_items oi JOIN orders o ON o.order_id = oi.order_id
WHERE  o.status = 'Отменён';                     -- 653

BEGIN;
DELETE FROM order_items AS oi
USING  orders AS o
WHERE  o.order_id = oi.order_id
  AND  o.status = 'Отменён';                     -- DELETE 653
ROLLBACK;
```

Попробуйте удалить клиента с заказами:

```sql
DELETE FROM customers WHERE customer_id = 72;
-- ERROR: update or delete on table "customers" violates foreign key constraint
--        "orders_customer_id_fkey" on table "orders"
```

Это и есть защита FK, которую восстановил скрипт 00. Каскад (`ON DELETE CASCADE`) показан на демо-таблицах
`m07_claim` / `m07_claim_item` (блок 4.4): претензия МолПром Регион на 5 позиций удаляется вместе с позициями.

Перенос в архив одной командой (блок 4.5):

```sql
WITH moved AS (
    DELETE FROM m07_call_log
    WHERE  call_date < DATE '2026-01-20'
    RETURNING *
)
INSERT INTO m07_call_archive SELECT * FROM moved;   -- INSERT 0 2
```

| | `DELETE` | `TRUNCATE` |
|---|---|---|
| `WHERE` | да | нет — вся таблица |
| скорость на больших таблицах | построчно, медленно | мгновенно |
| триггеры `ON DELETE` | срабатывают | нет (есть `ON TRUNCATE`) |
| identity | не меняется | `RESTART IDENTITY` — сбросить |
| FK на таблицу | проверяются построчно | запрещено без `CASCADE` |
| откат в транзакции | да | **да** (в PostgreSQL, в отличие от многих СУБД) |

## Шаг 8. UPSERT: INSERT … ON CONFLICT

```sql
INSERT INTO m07_edo_contact AS t (customer_id, email)
VALUES (1, 'buh@vektor-td.ru'),
       (6, 'zakaz@vkusdom.ru'),
       (7, 'edo@magnit-region.ru')
ON CONFLICT (customer_id) DO UPDATE
SET    email      = EXCLUDED.email,
       updated_at = now(),
       version    = t.version + 1
WHERE  t.email IS DISTINCT FROM EXCLUDED.email
RETURNING customer_id, email, version, (xmax = 0) AS inserted;
```

**Ожидаемо** (после шага 5.2 из `examples.sql`): 2 строки — id 1 обновлён (`version = 2`, `inserted = false`),
id 7 вставлен (`inserted = true`); id 6 не изменился и не возвращён.

`EXCLUDED` — строка, которую **пытались** вставить. `(xmax = 0)` — приём, позволяющий отличить вставку от обновления.

Типичные ошибки:
* `ON CONFLICT (email)` без уникального индекса на `email` → `there is no unique or exclusion constraint matching the ON CONFLICT specification`;
* два одинаковых ключа в одной команде → `ON CONFLICT DO UPDATE command cannot affect row a second time`.

## Шаг 9. MERGE: новый прайс-лист → products

Анализ до слияния:

```sql
SELECT CASE
           WHEN p.product_id IS NULL     THEN '3. новый SKU'
           WHEN p.base_price <> pl.price THEN '1. цена изменилась'
           ELSE                               '2. без изменений'
       END AS action,
       count(*) AS sku_count
FROM   price_list_2026 AS pl
LEFT   JOIN products   AS p ON p.sku = pl.sku
GROUP  BY 1 ORDER BY 1;
```

| action | sku_count |
|---|---|
| 1. цена изменилась | 23 |
| 2. без изменений | 10 |
| 3. новый SKU | 3 |

```sql
BEGIN;

MERGE INTO products AS p
USING price_list_2026 AS pl
   ON p.sku = pl.sku
WHEN MATCHED AND p.base_price <> pl.price THEN
    UPDATE SET base_price = pl.price
WHEN MATCHED THEN
    DO NOTHING
WHEN NOT MATCHED THEN
    INSERT (sku, product_name, category_id, unit, weight_kg, shelf_life_days,
            base_price, standard_cost, is_active, launch_date)
    VALUES (pl.sku, pl.product_name, pl.category_id, pl.unit, pl.weight_kg,
            pl.shelf_life_days, pl.price, pl.standard_cost, TRUE, pl.valid_from);
-- MERGE 26

SELECT product_id, sku, product_name FROM products WHERE product_id > 35;  -- 36, 37, 38

-- «WHEN NOT MATCHED BY SOURCE» в PG 16 нет — отдельной командой:
UPDATE products AS p
SET    is_active = FALSE, discontinued_date = DATE '2025-12-31'
WHERE  p.is_active
  AND  NOT EXISTS (SELECT 1 FROM price_list_2026 AS pl WHERE pl.sku = p.sku)
RETURNING p.sku, p.product_name;                                   -- SOU-002

ROLLBACK;
```

**Ожидаемо:** `MERGE 26` (23 обновления + 3 вставки; `DO NOTHING` не считается), новые товары получили id 36–38
из identity, выведен из ассортимента `SOU-002 Соус сливочно-чесночный`.

Сравнение с T-SQL:

| T-SQL `MERGE` | PostgreSQL 16 `MERGE` |
|---|---|
| обязательна `;` в конце | обычная команда |
| `WHEN NOT MATCHED [BY TARGET]` | `WHEN NOT MATCHED` |
| `WHEN NOT MATCHED BY SOURCE` | нет (появилось в PG 17) → отдельный `UPDATE/DELETE … WHERE NOT EXISTS` |
| `OUTPUT $action, inserted.*, deleted.*` | `RETURNING` нет (появился в PG 17) → контроль запросами до/после |
| — | `WHEN … THEN DO NOTHING` |

**Подумайте:** почему историю цен (`price_history`) одной командой `MERGE` обновить не получится? (Подсказка:
для изменившегося SKU нужно *и* закрыть старую строку, *и* вставить новую.) Ответ — блок 6.5 `examples.sql`:
`UPDATE 23` + `INSERT 23` в одной транзакции.
