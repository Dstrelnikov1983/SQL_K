Почему не MAX()+1?

Два менеджера одновременно регистрируют претензию поставщику:


INSERT INTO m07_supplier_note (note_id, supplier_name)
SELECT max(note_id) + 1, 'Вставка через MAX()+1'
FROM   m07_supplier_note;
  1. Что получит второй сеанс? Что будет, если PK нет?
  2. В демо после MAX()+1 следующая вставка через identity упала: duplicate key … m07_supplier_note_pkey. Почему?
  3. Sequence не откатывается при ROLLBACK — в нумерации будут «дырки». Это проблема?
⏱ 4 мин
1) Оба прочитают одинаковый MAX (snapshot), второй получит duplicate key; без PK — два одинаковых id. 2) Счётчик identity ничего не знает о «ручном» id 14 — nextval выдал 14. Лечение: setval(pg_get_serial_sequence(...), max). 3) Дырки — нормально для суррогатного ключа; если нужна сплошная нумерация (счета-фактуры по закону) — отдельный механизм с блокировкой, обсудим в модуле 11.

Квиз: GENERATED ALWAYS

Столбец call_id integer GENERATED ALWAYS AS IDENTITY. Что произойдёт при INSERT INTO m07_call_log (call_id, customer_id, topic) VALUES (1000, 1, 'X')?

  • Строка вставится с call_id = 1000
  • Значение 1000 будет проигнорировано, вставится следующее из счётчика
  • Ошибка: cannot insert a non-DEFAULT value into column "call_id"
  • Строка вставится, а счётчик продолжит с 1001

ALWAYS запрещает явное значение. Обойти можно только явно: INSERT … OVERRIDING SYSTEM VALUE VALUES (1000, …). Режим BY DEFAULT принял бы 1000, но счётчик об этом не узнает.

UPDATE — изменение строк

выражения · CASE · UPDATE … FROM · подзапросы · RETURNING

Правило: сначала SELECT, потом UPDATE — в транзакции


-- 1. Что и сколько изменим?
SELECT count(*) FROM orders WHERE shipped_date > required_date;   -- 984

-- 2. Изменяем в транзакции
BEGIN;
UPDATE orders
SET    comment = concat_ws('; ', btrim(comment),
                           'Отгрузка с опозданием ' || (shipped_date - required_date) || ' дн.')
WHERE  shipped_date > required_date;                              -- UPDATE 984 ✔ совпало

-- 3. Проверяем результат
SELECT order_id, comment FROM orders WHERE shipped_date > required_date LIMIT 3;

-- 4. Решаем
ROLLBACK;   -- или COMMIT;
Сверяйте счётчикОтвет сервера UPDATE n должен совпасть с числом из шага 1. Не совпал — ROLLBACK и разбираться.

UPDATE … FROM: изменение по данным другой таблицы

Коммерческий отдел прислал короткий файл с новыми ценами на молочную продукцию. Обновим products по совпадению sku.


-- таблица-источник: 4 новые цены
CREATE TEMP TABLE price_change (
    sku       varchar(20)   PRIMARY KEY,
    new_price numeric(10,2) NOT NULL
);
INSERT INTO price_change VALUES
    ('MLK-001',  94.00),
    ('MLK-004', 172.00),
    ('MLK-005', 259.00),
    ('MLK-099', 120.00);   -- такого SKU нет

BEGIN;
UPDATE products AS p
SET    base_price = pc.new_price
FROM   price_change AS pc
WHERE  pc.sku = p.sku
RETURNING p.product_id, p.sku, p.base_price;
-- UPDATE 3
ROLLBACK;
  • FROM добавляет вторую таблицу, а WHERE задаёт условие соединения.
  • В SET доступны столбцы источника: pc.new_price.
  • Меняются только строки цели, у которых нашлась пара. Строка источника без пары (MLK-099) ни на что не влияет.
  • Целевую таблицу в FROM не повторяем. (T-SQL: UPDATE p SET … FROM products p JOIN ….)
ЛовушкаЕсли для одной строки цели в источнике окажется несколько строк, PostgreSQL молча возьмёт одну из них, причём неизвестно какую. Источник должен давать одну строку на ключ, поэтому здесь у sku стоит PRIMARY KEY (или агрегируйте источник).
Посложнее — в examples.sql (3.4б)Пересчёт standard_cost: в источнике в FROM стоит подзапрос с рецептурой и средними ценами закупок.

Схема: как выполняется UPDATE … FROM

UPDATE products AS p -- ③ цель: что меняем SET base_price = pc.new_price -- ③ значение из источника FROM price_change AS pc -- ① источник WHERE pc.sku = p.sku -- ② соединение RETURNING p.product_id, p.sku, p.base_price;

05

UPSERT и MERGE

«вставить или обновить» · слияние источника с целью

INSERT … ON CONFLICT


INSERT INTO m07_edo_contact AS t (customer_id, email)
VALUES (1, 'buh@vektor-td.ru'),
       (6, 'zakaz@vkusdom.ru'),          -- адрес не изменился
       (7, 'edo@magnit-region.ru')       -- новой строки ещё нет
ON CONFLICT (customer_id) DO UPDATE
SET    email      = EXCLUDED.email,      -- EXCLUDED = строка, которую пытались вставить
       updated_at = now(),
       version    = t.version + 1
WHERE  t.email IS DISTINCT FROM EXCLUDED.email
RETURNING customer_id, version, (xmax = 0) AS inserted;
-- 1 | 2 | false      7 | 1 | true      (id 6 не тронут)
ВариантыDO NOTHING — пропустить дубликаты; DO UPDATE … WHERE — обновить только изменившееся.
ТребованияНужен UNIQUE/PK на столбцах конфликта. Один ключ дважды в одной команде → cannot affect row a second time.

MERGE (PostgreSQL 15+): новый прайс-лист → products


MERGE INTO products AS p
USING price_list_2026 AS pl
   ON p.sku = pl.sku
WHEN MATCHED AND p.base_price <> pl.price THEN
    UPDATE SET base_price = pl.price
WHEN MATCHED THEN
    DO NOTHING
WHEN NOT MATCHED THEN
    INSERT (sku, product_name, category_id, unit, weight_kg, shelf_life_days,
            base_price, standard_cost, is_active, launch_date)
    VALUES (pl.sku, pl.product_name, pl.category_id, pl.unit, pl.weight_kg,
            pl.shelf_life_days, pl.price, pl.standard_cost, TRUE, pl.valid_from);
-- MERGE 26  = 23 изменения цены + 3 новых SKU (id 36–38 выдал identity)
  • WHEN-ветки проверяются по порядку, срабатывает первая подходящая.
  • Строка цели может совпасть только с одной строкой источника — иначе MERGE command cannot affect row a second time.

Схема: как MERGE раскладывает строки по веткам

MERGE INTO products AS p USING price_list_2026 AS pl -- источник: 36 строк ON p.sku = pl.sku -- ① сопоставление WHEN MATCHED AND p.base_price <> pl.price THEN -- ② цена изменилась UPDATE SET base_price = pl.price WHEN MATCHED THEN -- ③ цена та же DO NOTHING WHEN NOT MATCHED THEN -- ④ нового SKU нет в products INSERT (sku, product_name, category_id, unit, weight_kg, shelf_life_days, base_price, standard_cost, is_active, launch_date) VALUES (pl.sku, pl.product_name, pl.category_id, pl.unit, pl.weight_kg, pl.shelf_life_days, pl.price, pl.standard_cost, TRUE, pl.valid_from);
Как читать схему① Каждую строку источника ищем в цели по условию ON, как при LEFT JOIN источника к цели. Затем проверяем WHEN-ветки сверху вниз, и срабатывает первая подходящая: ② UPDATE, ③ DO NOTHING, ④ INSERT. Строки цели без пары в источнике MERGE в PG 16 не трогает. Нажимайте →

Квиз: UPSERT или MERGE?

Ежедневно загружаем остатки склада (ключ — material_id): новые материалы вставить, существующие обновить, отсутствующие в выгрузке — обнулить. Что выбрать в PostgreSQL 16?

  • Только INSERT … ON CONFLICT DO UPDATE
  • Один MERGE с WHEN NOT MATCHED BY SOURCE
  • MERGE (или ON CONFLICT) + отдельный UPDATE … WHERE NOT EXISTS в одной транзакции
  • DELETE всех строк и INSERT заново

В PG 16 нет NOT MATCHED BY SOURCE, поэтому «обнулить отсутствующие» — отдельной командой. Транзакция гарантирует, что отчёты не увидят промежуточное состояние. DELETE+INSERT теряет историю и ломает FK.

Опрос: самая опасная операция

Какая команда, по-вашему, чаще всего приводит к инцидентам с данными?

  • UPDATE без (точного) WHERE0
  • DELETE / TRUNCATE … CASCADE0
  • UPDATE … FROM с дублями источника0
  • MERGE / UPSERT при повторном запуске0
Правильного ответа нет — обсудите, как каждая из ошибок обнаруживается: счётчик строк, контрольный запрос, идемпотентность скрипта (повторный запуск не должен менять результат).

Итоги: что запомнить

Безопасность

  • личная схема и current_schema()
  • SELECT перед UPDATE/DELETE
  • BEGIN … ROLLBACK для «что если»
  • сверяйте счётчик строк

Синтаксис PG

  • RETURNING вместо OUTPUT
  • UPDATE … FROM, DELETE … USING
  • identity, а не MAX()+1
  • CTE с DELETE/UPDATE … RETURNING

Слияние

  • ON CONFLICT — нужен UNIQUE
  • MERGE: одна строка источника на строку цели
  • NOT MATCHED BY SOURCE — отдельной командой
  • скрипты загрузки — идемпотентны
