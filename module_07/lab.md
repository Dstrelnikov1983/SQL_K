# Модуль 7. Лабораторная работа «Наводим порядок в данных»

| | |
|---|---|
| **Цель** | Применить `INSERT`, `UPDATE`, `DELETE`, `UPSERT` и `MERGE` для исправления ошибок учёта и загрузки внешних данных; оценить, сколько денег стоят найденные ошибки |
| **Время** | 35 минут на занятии + 10 минут защита выводов; незавершённые задания и задания со звёздочкой — самостоятельно |
| **Формат** | Команды по 3–4 человека; каждый выполняет запросы в **своей** личной схеме, команда сводит результаты |
| **Сдаётся** | SQL-файл с решениями (с комментариями) + 5–7 предложений «Вывод для руководства» |

## Общая часть (для обеих команд, 5 минут)

1. Подключитесь к БД и установите путь поиска:

   ```sql
   SET search_path TO stud_<фамилия>, pitanie, public;
   SELECT current_schema();          -- должно быть stud_<фамилия>, НЕ pitanie
   ```

   Если личной схемы ещё нет — выполните `module_07/scripts/00_personal_schema.sql` (см. практическую работу, шаг 0).
2. Приведите данные в исходное состояние: `module_07/scripts/01_reset_data.sql`.
3. Загрузите данные своей команды:

   | Команда А | Команда Б |
   |---|---|
   | `02_load_price_list_2026.sql` — прайс-лист 2026 (36 строк) | `03_load_supplier_price_offer.sql` — предложения поставщиков (18 строк) |
   | | `04_load_recipe_norms_2026.sql` — новые нормы расхода (12 строк) |
   | | `05_lab_b_receipt_glitch.sql` — сбой интеграции со складом (+18 строк в `purchase_order_items`) |

   Исходные файлы данных — в `module_07/data/*.csv` (UTF-8, разделитель `;`).
4. **Правила безопасности** (оцениваются!):
   * перед каждым `UPDATE`/`DELETE` — `SELECT` с тем же условием и подсчёт строк;
   * опасные изменения — внутри `BEGIN … COMMIT/ROLLBACK`; сверяйте число строк в ответе сервера с ожидаемым;
   * после изменения — контрольный запрос.
5. Если что-то пошло не так — `01_reset_data.sql` и повторная загрузка данных команды (п. 3).

## Вариант 1 — Команда А «Финансы и продажи»

> Финансовый директор жалуется: «В CRM грязь — письма уходят не туда, одни и те же клиенты заведены по 2–3 раза,
> коммерческая служба прислала новый прайс, а один из дистрибьюторов давно должен больше лимита — и мы продолжаем ему отгружать».

### Задание А1. Чистка e-mail клиентов (UPDATE с выражением)

Приведите `customers.email` к нижнему регистру без пробелов по краям; пустую строку замените на `NULL`.

*Подсказки:* `lower()`, `btrim()`, `nullif()`. Условие `WHERE email IS DISTINCT FROM <новое значение>` — чтобы
не обновлять строки, которые и так корректны (и чтобы счётчик строк был честным).

**Проверка:** должно быть изменено **32** строки; после обновления запрос
`WHERE email <> lower(btrim(email))` возвращает 0 строк.

### Задание А2. Единый формат телефонов (UPDATE … FROM подзапроса)

Приведите все телефоны клиентов к формату `+7 (XXX) XXX-XX-XX`.

*Подсказки:*
1. Сначала получите только цифры: `regexp_replace(phone, '\D', '', 'g')`. Какой длины строки получились? С какой цифры начинаются?
2. Соберите номер функцией `format('+7 (%s) %s-%s-%s', substr(...), …)`.
3. Обновляйте только номера из 11 цифр, начинающиеся с 7 или 8, и только те, что ещё не в нужном формате.
4. Проверка формата — регулярное выражение `'^\+7 \(\d{3}\) \d{3}-\d{2}-\d{2}$'`.

**Проверка:** изменено **50** строк; все 73 номера соответствуют формату.

### Задание А3. Найти дубли клиентов и составить таблицу соответствий (CREATE TABLE + INSERT … SELECT)

1. Найдите ИНН, под которыми заведено больше одного клиента. Выведите ИНН, число записей и список `customer_id`.
2. Создайте таблицу `customer_merge_map (dup_id PK, main_id → customers, inn, dup_name)`.
3. Заполните её одной командой `INSERT … SELECT`: основная запись — с **минимальным** `customer_id` для ИНН,
   все остальные — дубли. Используйте `RETURNING`, чтобы сразу увидеть результат.

**Проверка:** 3 ИНН; в `customer_merge_map` **4** строки.

### Задание А4. Объединить дубли (UPDATE … FROM + DELETE … USING в транзакции)

1. В одной транзакции перенесите заказы дублей на основную запись (`UPDATE orders … FROM customer_merge_map`)
   и удалите записи-дубли (`DELETE FROM customers … USING customer_merge_map`).
2. Что случится, если поменять команды местами? Проверьте (в транзакции с `ROLLBACK`).
3. Посчитайте выручку объединённых клиентов (не отменённые заказы) — насколько изменилась картина по «Ромашке»?

**Проверка:** `UPDATE 179`, `DELETE 4`; клиентов **69**, у клиента 2 («Ромашка») **230** заказов.

### Задание А5. MERGE нового прайс-листа в справочник товаров

Источник — таблица `price_list_2026` (36 SKU).

1. Запросом с `LEFT JOIN` определите, сколько SKU изменили цену, сколько не изменили, сколько новых.
2. Напишите `MERGE INTO products … USING price_list_2026 ON sku`:
   * совпало и цена другая → `UPDATE base_price`;
   * совпало и цена та же → ничего не делать;
   * не найдено → `INSERT` нового товара (`launch_date = valid_from`, `is_active = TRUE`; ключ не указывайте — его выдаст identity).
3. Товары, которых нет в прайсе, но они активны, — выведите из ассортимента (`is_active = FALSE`, `discontinued_date = '2025-12-31'`).
   Почему это нельзя сделать внутри `MERGE` в PostgreSQL 16?

**Проверка:** анализ — 23 / 10 / 3; сервер отвечает `MERGE 26`; выведен 1 товар; всего товаров **38**, активных **36**.

### Задание А6. История цен (SCD-2): закрыть старые цены, открыть новые

Для каждого товара в `price_history` должна быть ровно одна действующая цена (`valid_to IS NULL`), равная `products.base_price`.

1. `UPDATE price_history … FROM`: проставьте `valid_to = '2025-12-31'` действующим ценам, которые изменились, и цене выведенного товара.
2. `INSERT … SELECT`: откройте цены 2026 (`valid_from = '2026-01-01'`) для всех товаров прайса, у которых нет действующей цены.
3. Обе команды — в одной транзакции. Почему это важно?

**Проверка:** `UPDATE 24`, `INSERT 26`; контрольный запрос «активных товаров — 36, с действующей ценой — 36, расхождений с `base_price` — 0».

### Задание А7. Цена ниже себестоимости (CTE с модификацией данных)

1. Найдите активные товары, у которых прайс **с максимально допустимой скидкой 10 %** ниже `standard_cost`.
2. Посчитайте фактическую валовую маржу этих товаров в 2025 г. (формула — в README).
3. Одной командой (`WITH upd AS (UPDATE … RETURNING …), closed AS (UPDATE price_history …) INSERT INTO price_history …`):
   * установите новую цену `ceil(standard_cost * 1.25)`;
   * закройте действующую цену 31.01.2026;
   * откройте новую с 01.02.2026.

**Проверка:** 2 товара; маржа 2025 г. — отрицательная (суммарно около −4,2 млн руб.); новые цены 257.00 и 189.00.

**Подумайте:** коммерческая служба прислала прайс 2026 года — почему проблема не была исправлена в нём? Какие
данные команде Б стоит запросить, чтобы найти причину роста себестоимости?

### Задание А8. Стоп-лист должников

1. Создайте таблицу `credit_stop_list`: `stop_id` (identity), `customer_id` (уникальный, FK), `debt`, `credit_limit`, `reason`, `added_at DEFAULT now()`.
2. Одной командой `INSERT … SELECT` внесите клиентов, у которых сумма неоплаченных счетов (`invoices.amount` −
   оплаты из `payments`) превышает `credit_limit`.
3. Добавьте в `orders` столбец `is_blocked boolean NOT NULL DEFAULT FALSE` и заблокируйте **неотгруженные**
   заказы (статусы «Новый», «В работе») клиентов из стоп-листа, дописав причину в `comment`.
4. Через месяц проверку повторят. Перепишите вставку так, чтобы повторный запуск не падал на уникальности, а обновлял сумму долга.

**Проверка:** в стоп-листе **1** клиент с долгом **6 907 600,45** руб. при лимите 3 000 000; заблокирован 1 заказ.

### Задание А9*. Архив отменённых заказов

Перенесите отменённые заказы 2024 г. (без счетов и возвратов) и их позиции в таблицы `orders_archive`,
`orders_archive_items` (`CREATE TABLE … (LIKE …)`). Используйте `DELETE … RETURNING` внутри CTE. В каком порядке
удалять позиции и заказы и почему?

**Проверка:** 314 позиций, 83 заказа; в `orders` осталось 4375.

### Вывод для руководства (команда А)

Сформулируйте 5–7 предложений с цифрами:
* сколько контактов было «грязными» и чем это грозит (ЭДО, рассылка счетов);
* сколько дублей клиентов найдено и как изменилась выручка/рейтинг клиента после объединения;

## Вариант 2 — Команда Б «Производство и закупки»

> Директор по производству: «Закупщики работают по старым ценам, в учёте висят незакрытые простои, после перехода
> на новую складскую систему приёмки задвоились, технолог прислал новые нормы. Наведите порядок и скажите, от каких
> поставщиков пора отказаться».

### Задание Б1. Таблица контрактных цен (CREATE TABLE + INSERT … SELECT)

1. Создайте `supplier_contract_prices (supplier_id, material_id, contract_price, valid_from, source, updated_at DEFAULT now())`
   с составным первичным ключом `(supplier_id, material_id)`, внешними ключами и `CHECK (contract_price > 0)`.
2. Заполните её **последней** ценой закупки 2025 г. для каждой пары «поставщик — материал», `source = 'Закупки 2025'`.

*Подсказка:* `SELECT DISTINCT ON (po.supplier_id, poi.material_id) … ORDER BY po.supplier_id, poi.material_id, po.order_date DESC, poi.po_item_id DESC`.

**Проверка:** **40** строк; по сахару (`material_id = 4`) — три поставщика, самая высокая цена — 84.73 (АгроСнаб-М).

### Задание Б2. MERGE коммерческих предложений

Источник — `supplier_price_offer` (18 предложений; поставщик указан **ИНН**).

1. Найдите предложения от контрагентов, которых нет в `suppliers`.
2. Классифицируйте предложения: цена ниже действующей / выше / та же / новая пара.
3. Оцените экономию от принятия снижений на объёмах закупок 2025 г.
4. Выполните `MERGE`: источник — предложения, соединённые с `suppliers` по ИНН;
   * совпало и цена **ниже** → обновить цену, `valid_from`, `source = 'КП 2026'`, `updated_at`;
   * совпало, но цена не ниже → ничего не делать (политика: повышения не принимаем автоматически);
   * новая пара → вставить с `source = 'КП 2026 (новая пара)'`.

**Проверка:** неизвестный контрагент — 1 («ВкусЭкспорт»); классификация 9 / 3 / 1 / 4; экономия ≈ **3,1 млн руб.**;
сервер отвечает `MERGE 13`; итог по `source`: 31 / 9 / 4.

### Задание Б3. Закрыть незакрытые простои (ALTER TABLE + UPDATE … FROM)

1. Найдите простои с `end_time IS NULL`.
2. Добавьте столбец `end_time_estimated boolean NOT NULL DEFAULT FALSE`.
3. Проставьте `end_time = start_time + средняя длительность закрытых простоев той же линии и той же категории`
   (округлите до минут: `date_trunc('minute', …)`), пометьте `end_time_estimated = TRUE`. Выведите результат через `RETURNING`.

**Проверка:** **4** строки; незакрытых простоев не осталось; оценки — от 1 ч 18 мин до 1 ч 35 мин.

**Подумайте:** почему нельзя просто удалить такие строки? А заменить `end_time` на `start_time`?

### Задание Б4. Ошибочные приёмки (UPDATE … FROM self-join + DELETE)

После сбоя WMS в ноябре 2025 г. часть позиций приёмки записана дважды.

1. Найдите пары `(po_id, material_id)`, встречающиеся в `purchase_order_items` более одного раза.
2. Добавьте столбец `receipt_error varchar(50)` и пометьте ошибочную строку каждой пары (с бо́льшим `po_item_id`)
   текстом `'Двойной ввод (сбой WMS 11.2025)'`. *Подсказка:* соединение таблицы с самой собой в `UPDATE … FROM`.
3. Оцените, на какую сумму завышена стоимость приёмки (`quantity * unit_price`).
4. Удалите помеченные строки.

**Проверка:** **18** пар, помечено 18 строк на **2 570 703,33** руб.; после удаления — 2328 строк.

### Задание Б5. Новые нормы расхода (UPSERT)

Технолог прислал карту норм `recipe_norms_2026`: часть норм изменилась, часть новая, часть без изменений.

1. Выполните `INSERT INTO recipes … SELECT … FROM recipe_norms_2026 ON CONFLICT (product_id, material_id) DO UPDATE …`.
   Почему команда завершается ошибкой? Найдите причину в данных.
2. Исправьте: оставьте одну строку на пару (`DISTINCT ON`, последнюю по `line_no`) и обновляйте только реально
   изменившиеся нормы (`WHERE … IS DISTINCT FROM EXCLUDED…`). Выведите, какие строки вставлены, какие обновлены
   (приём: `(xmax = 0) AS inserted`).

**Проверка:** первая попытка — `ON CONFLICT DO UPDATE command cannot affect row a second time`; вторая —
8 строк (4 вставлено, 4 обновлено); в `recipes` **150** строк.

**Подумайте:** технолог снизил норму клубничного наполнителя. Поможет ли это сократить списания наполнителя? Где
настоящая причина списаний (вспомните модули 4–5)?

### Задание Б6. Стоп-лист поставщиков (INSERT … SELECT + ON CONFLICT)

1. Создайте `supplier_stop_list (supplier_id PK/FK, reason, added_at DEFAULT now())`.
2. **Критерий 1 — переплата:** внесите поставщиков, у которых средняя цена 2025 г. хотя бы по одному материалу
   более чем на 15 % выше лучшей средней цены по этому материалу. В `reason` укажите число таких материалов и
   максимальную переплату в %.
3. **Критерий 2 — опоздания:** средняя задержка поставки 2025 г. (`received_date − expected_date`) больше 2 дней.
   Если поставщик уже в списке — допишите причину через `ON CONFLICT … DO UPDATE SET reason = sl.reason || '; ' || EXCLUDED.reason`.

**Проверка:** 2 поставщика — ООО «АгроСнаб-М» (10 материалов, до +27 %) и ООО «МолПром Регион» (2,8 дн.).

### Задание Б7*. «Что если» отказаться от АгроСнаб-М

### Вывод для руководства (команда Б)

5–7 предложений с цифрами:
