SUM, AVG и NULL


SELECT COUNT(*)                           AS suppliers,
       COUNT(rating)                      AS rated,
       ROUND(AVG(rating), 2)              AS avg_rating,
       ROUND(AVG(COALESCE(rating, 0)), 2) AS avg_null_as_0
FROM   suppliers;

SELECT SUM(amount),                 -- NULL
       COALESCE(SUM(amount), 0),    -- 0
       COUNT(*)                     -- 0
FROM   payments
WHERE  payment_date > DATE '2030-01-01';
Все агрегаты, кроме COUNT(*), игнорируют NULLAVG = SUM(не-NULL) / COUNT(не-NULL). Новый поставщик без рейтинга не «тянет» среднее вниз.
SUM пустого набора — NULLВ отчётах и арифметике оборачивайте в COALESCE(SUM(...), 0), иначе выручка - NULL = NULL.
MIN / MAXРаботают с числами, датами и строками: MIN(order_date) = 2024-01-01, MAX(discount_pct) = 25.00.

Квиз: AVG и NULL

В столбце rating значения: 4, 5, NULL, 3. Что вернёт AVG(rating)?

  • 3.00
  • 4.00
  • NULL
  • Ошибку

NULL игнорируется: (4 + 5 + 3) / 3 = 4. Если бы NULL считался нулём — получили бы 3. Если все значения NULL — AVG вернёт NULL.

Квиз: где поставить условие?

Нужны линии, у которых в 2025 г. суммарный брак превысил 30 000 шт. Как правильно?

  • Оба условия в WHERE
  • Оба условия в HAVING
  • Год — в WHERE, SUM(defect_qty) > 30000 — в HAVING
  • Год — в HAVING, сумма — в WHERE

Фильтр по году относится к строкам — в WHERE (до группировки, меньше работы). Условие на сумму — к группе, только HAVING. Вариант «оба в HAVING» не сработает: production_date не в GROUP BY.

Типичная ошибка: среднее от процентов


SELECT ROUND(AVG(100.0 * defect / produced), 2)
         AS avg_of_pct,        -- 25.50
       ROUND(100.0 * SUM(defect) / SUM(produced), 2)
         AS weighted_pct       -- 1.49
FROM   (VALUES (10, 5),        -- 50 % брака
               (1000, 10))     --  1 % брака
       AS t (produced, defect);

На данных «Питание +»: среднее по 10 ячейкам «линия × смена» — 2,391 %, реальный процент брака — 2,520 %.

AVG(процент) даёт каждой группе одинаковый весПартия из 10 штук влияет так же, как партия из 1000.
ПравильноSUM(часть) / SUM(целое): процент брака, доля возвратов, выполнение плана, средняя цена (SUM(qty*price)/SUM(qty)), средняя скидка в рублях.
Где ещёСредняя скидка Павлова: простая 5,23 %, взвешенная по сумме — 6,42 %. Крупным заказам он даёт бо́льшие скидки.

Какие показатели можно складывать?

Финансовый аналитик собрал отчёт по месяцам, а итог года посчитал в Excel как сумму (или среднее) месячных строк. Для каких показателей «Питание +» это правильно, а для каких — нет?

Показатель по месяцамИтог года = сумма месяцев?
Выручка, руб.
Число активных клиентов (COUNT DISTINCT)
Процент брака
Средний чек
Дебиторская задолженность на конец месяца
⏱ 4 мин
Выручка — аддитивна (сумма). Активные клиенты — неаддитивны: один клиент активен в нескольких месяцах; итог — COUNT(DISTINCT) за год (в наших данных 72 клиента за период, а сумма по месяцам — сотни). Процент брака — неаддитивен: SUM(defect)/SUM(produced) за год, не сумма и не AVG месячных процентов. Средний чек — SUM(выручка)/COUNT(заказов) за год. Задолженность на дату — полуаддитивна: по клиентам складывается, по времени — нет (берётся значение на конец года). Вывод: ROLLUP в SQL пересчитывает агрегат по исходным строкам, поэтому итоги верны для любых агрегатов.

       ROUND(SUM(t.revenue) / 1e6, 2)   AS revenue_mln,
       GROUPING(t.yr, t.qtr)            AS bits
FROM   (... выручка строки с yr, qtr ...) AS t
GROUP  BY ROLLUP (t.yr, t.qtr);

CUBE: все комбинации итогов


SELECT CASE WHEN GROUPING(b.line_id) = 1
            THEN 'Все линии'
            ELSE 'Линия ' || b.line_id END AS line,
       CASE WHEN GROUPING(b.shift) = 1
            THEN 'Обе смены'
            ELSE b.shift END             AS shift,
       ROUND(100.0 * SUM(b.defect_qty)
                   / SUM(b.produced_qty), 2) AS defect_pct
FROM   production_batches AS b
GROUP  BY CUBE (b.line_id, b.shift);

GROUPING SETS: несколько отчётов за один проход


SELECT o.channel,
       c.customer_type,
       ROUND(SUM(oi.quantity * oi.unit_price
             * (1 - oi.discount_pct / 100)) / 1e6, 2)
         AS revenue_mln
FROM   orders      AS o
JOIN   order_items AS oi ON oi.order_id   = o.order_id
JOIN   customers   AS c  ON c.customer_id = o.customer_id
WHERE  o.status <> 'Отменён'
  AND  o.order_date >= DATE '2025-01-01'
GROUP  BY GROUPING SETS ((o.channel),
                         (c.customer_type),
                         ());

ROLLUP в SQL или итоги в BI?

Аналитик говорит: «Зачем ROLLUP и CUBE? Power BI / Excel сами посчитают итоги». Когда итоги нужно считать в SQL, а когда — в инструменте визуализации?

⏱ 4 мин
В SQL: когда отчёт выгружается «как есть» (CSV, e-mail, регламентная форма); когда итог неаддитивен и BI посчитает неверно (COUNT DISTINCT клиентов, медиана, взвешенный процент — BI может суммировать проценты); когда объёмы большие и нужно уменьшить передаваемые данные; для контроля цифр (эталонный запрос). В BI: когда нужна интерактивная детализация, срезы на лету; меры в DAX правильно пересчитываются в контексте. Важно: один источник истины для формулы показателя.

Что запомнить

Агрегаты

  • все, кроме COUNT(*), игнорируют NULL
  • SUM пустого набора — NULL
  • FILTER (WHERE …) — условная агрегация
  • COUNT(DISTINCT) после JOIN

Группировка

  • FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
  • строки — WHERE, группы — HAVING
  • «одна строка результата — это что?»

Отчёты

  • ROLLUP — иерархия, CUBE — все комбинации, GROUPING SETS — свой список
  • подписи — через GROUPING()
  • проценты — SUM/SUM, не AVG
