Data-driven management

Руководство решает не «по ощущениям», а на основе проверяемых данных. Чтобы убедить совет директоров, аналитики должны показать конкретные деньги.

1. Вопрос

Где мы теряем деньги? Почему план не выполнен?

2. Данные

Какие таблицы и поля отвечают на вопрос? Можно ли им верить?

3. Анализ

SQL-запрос: метрика, разрез, сравнение с нормой

4. Находка

«Сколько рублей и почему» — с доказательством

5. Решение

Изменить политику, процесс, поставщика, режим

6. Контроль

Повторяемый запрос / представление / процедура для мониторинга

Что делает аналитическую находку убедительной?

Вы приходите к генеральному директору с фразой: «У нас проблемы со скидками». Что он спросит? Что должно быть в вашей находке, чтобы он принял решение сегодня?

⏱ 4 мин
Ожидаемые ответы: конкретная сумма в рублях и период; сравнение с нормой/политикой/бенчмарком (у остальных — X); кто/что/где (разрез: менеджер, клиент, линия); воспроизводимость — запрос можно перепроверить; качество данных (не артефакт ли это дублей/NULL); причина, а не только симптом; конкретное действие и ожидаемый эффект; как будем контролировать. Правила работы с общей БД

Схема pitanie — только чтениеОна общая для всех групп. Никаких INSERT, UPDATE, DELETE, CREATE в ней. Ошибка permission denied — это защита, а не баг.
Личная схема stud_<фамилия>С модуля 7 вы создаёте свою схему и копии нужных таблиц. В ней можно изменять данные, создавать представления, функции, процедуры.
  • Не трогайте чужие схемы и объекты — БД общая.
  • Тяжёлые запросы проверяйте с LIMIT; зависший запрос — кнопка «Отмена» в DBeaver или pg_cancel_backend().
  • Не оставляйте открытые транзакции: в DBeaver по умолчанию включён Auto-Commit — не выключайте его без необходимости (модуль 11).
  • Пароль — личный: не коммитьте его в Git и не публикуйте в чатах.

Квиз: защищённое подключение

Какой режим sslmode одновременно шифрует трафик и проверяет, что вы подключились именно к серверу rc1a-…mdb.yandexcloud.net?

  • prefer
  • require
  • verify-ca
  • verify-full

require шифрует, но не проверяет сертификат; verify-ca проверяет подпись центра сертификации, но не имя хоста; verify-full проверяет и подпись (по root.crt), и соответствие имени хоста — защита от подмены сервера.

Разведка через системный каталог


-- Какие таблицы есть и что в них
SELECT t.table_name,
       obj_description(
         format('%I.%I', t.table_schema,
                t.table_name)::regclass
       ) AS description
FROM   information_schema.tables AS t
WHERE  t.table_schema = 'pitanie'
  AND  t.table_type   = 'BASE TABLE'
ORDER  BY t.table_name;


-- Кто на кого ссылается
SELECT con.conrelid::regclass  AS child_table,
       a.attname               AS fk_column,
       con.confrelid::regclass AS parent_table
FROM   pg_constraint AS con
JOIN   pg_attribute  AS a
       ON  a.attrelid = con.conrelid
       AND a.attnum   = ANY (con.conkey)
WHERE  con.contype      = 'f'
  AND  con.connamespace = 'pitanie'::regnamespace
ORDER  BY 1::text, 2;
Результат23 таблицы с комментариями; 30 внешних ключей, из них 2 — самоссылки: employees.manager_id (иерархия) и product_categories.parent_category_id (классификатор).

Ответ: 100.0 переводит вычисление в numeric (иначе целочисленное деление даст 0); NULLIF(x, 0) защищает от деления на ноль, возвращая NULL. Код из module_00/examples.sql, разделы 5.1–5.2.

Квиз: прочитай данные

В customers 73 строки, у 21 клиента email IS NULL, у 3 — region_id IS NULL. Что вернёт запрос?


SELECT COUNT(*), COUNT(email), COUNT(region_id)
FROM   customers;
  • 73, 73, 73
  • 73, 52, 70
  • 52, 52, 70
  • 73, 21, 3

COUNT(*) считает строки, COUNT(столбец) — только не-NULL значения. Пропуски в данных — первое, что проверяет аналитик: на них «теряются» клиенты в соединениях и отчётах.

Связанные с SQL темы: карта

Теория

Реляционная алгебра (Кодд, 1970): σ выборка, π проекция, ⋈ соединение, ∪ − ∩ — основа SQL и оптимизатора.
Нормализация 1НФ–3НФ, НФБК: устранение избыточности (дубли клиентов — её нарушение).

Стандарт SQL

SQL-92 → SQL:1999 (рекурсия, триггеры) → SQL:2003 (окна, MERGE) → SQL:2016 (JSON, MATCH_RECOGNIZE) → SQL:2023 (SQL/PGQ — графовые запросы, JSON-тип).

Производительность

Индексы (B-tree, GIN, BRIN), планы выполнения EXPLAIN ANALYZE, статистика, секционирование.

Хранилища и OLAP

DWH, схема «звезда»: факты и измерения, ETL/ELT, колоночные СУБД (ClickHouse, Greenplum), ROLLUP/CUBE как OLAP в SQL.

Вокруг SQL

NoSQL: документные (MongoDB), ключ-значение (Redis), графовые (Neo4j); CAP.
ORM: SQLAlchemy, Hibernate, Django ORM — SQL «под капотом».

BI и аналитика

Power BI (DAX), Yandex DataLens, Superset, Tableau; Python + pandas; dbt — SQL-трансформации как код.
Не углубляться — показать, что SQL в центре экосистемы данных. Для системных аналитиков особенно важны: нормализация (проектирование), EXPLAIN (диалог с разработчиками о производительности), DWH/BI (куда уходят их запросы). Индексы и EXPLAIN будем упоминать в модулях 3, 5 и 9.

Квиз: связанные темы

Аналитик подозревает, что отчёт по скидкам работает медленно из-за полного просмотра order_items. Какой инструмент PostgreSQL покажет, как СУБД выполняет запрос?

  • DESCRIBE order_items
  • EXPLAIN ANALYZE SELECT …
  • SHOW PLAN FOR SELECT …
  • VACUUM order_items

EXPLAIN показывает план (Seq Scan, Index Scan, Hash Join…) и оценки стоимости; с ANALYZE запрос реально выполняется и выводятся фактические время и число строк. DESCRIBE — команда MySQL/Oracle, VACUUM — обслуживание таблиц.
