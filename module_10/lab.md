# Модуль 10. Лабораторная работа
## «Автоматизируем проверки»: PL/pgSQL-блоки, функции и обработка ошибок

| | |
|---|---|
| **Цель** | С помощью PL/pgSQL автоматизировать регулярные проверки своей команды: пройти циклом по объектам (менеджерам, линиям, поставщикам), классифицировать их, создать функции расчёта потерь с проверкой параметров и устойчивой обработкой ошибок |
| **Время** | 80 мин в аудитории + доработка дома |
| **Формат** | В группах по командам (2–4 человека), каждый выполняет в своей личной схеме; итоговый вывод — общий |
| **Сдаётся** | Скрипт `lab10_<фамилия>.sql` (выполняется целиком без ошибок, кроме помеченных `-- ОЖИДАЕМАЯ ОШИБКА`) + текст «Вывод для руководства» |
| **Эталон** | `lab_solutions.sql` (у преподавателя) |

## Общая часть (5 мин)

1. Личная схема — `stud_<фамилия>` (если её нет: `SET course.stud_schema = 'stud_ivanov';` и выполнить `module_07/scripts/00_personal_schema.sql`). В начале скрипта:

   ```sql
   SET search_path TO stud_ivanov, pitanie, public;
   ```

   В личной схеме есть копии таблиц `pitanie` с теми же именами — исходные данные читайте **с префиксом** `pitanie.`.

2. Включите вывод `RAISE NOTICE` в клиенте (DBeaver: панель *Output*). Блок `DO $$ ... $$;` выполняйте целиком.
3. **Соглашения:** переменные — `v_`, параметры — `p_`, константы — `c_`. Каждый `DO`-блок и функцию сопровождайте комментарием «что делает».
4. Функции создавайте в личной схеме (`CREATE OR REPLACE FUNCTION stud_ivanov.fn_...`), данные читайте из `pitanie.*`.
5. Формулы:
   * выручка строки — `quantity * unit_price * (1 - discount_pct / 100)`, отменённые заказы исключаем;
   * политика скидок — не более **10 %**;
   * дата среза — **31.12.2025**.

## Вариант 1 — Команда А «Финансы и продажи»

> **Контекст.** Финансовый директор хочет, чтобы ежемесячные проверки — «кто из менеджеров нарушает политику скидок», «сколько пени можно предъявить должникам», «как идём к плану» — выполнялись одним скриптом и не «падали» на первой же ошибке.

### Задание А1. DO-блок «Менеджеры и политика скидок»

Пройдите циклом `FOR r IN SELECT ...` по всем менеджерам, у которых есть продажи, и для каждого выведите `RAISE NOTICE`: ФИО, число строк, число строк со скидкой > 10 % и их долю, среднюю скидку, сумму скидки **сверх** 10 % в рублях и класс:

| Класс | Условие |
|---|---|
| `КРИТИЧНО` | доля строк сверх лимита ≥ 50 % **или** средняя скидка > 15 % |
| `внимание` | есть хотя бы одна строка сверх лимита |
| `норма` | иначе |

*Подсказки:*
1. Объявите константу `c_limit CONSTANT numeric := 10`.
2. Сумма сверх лимита: `SUM(quantity * unit_price * (discount_pct - c_limit) / 100) FILTER (WHERE discount_pct > c_limit)`, оберните в `COALESCE(..., 0)`.
3. Классификацию сделайте выражением `CASE` и присвойте переменной `v_class`.
4. Посчитайте в отдельной переменной число критичных и выведите в конце.

**Проверка:** **9** строк вывода; критичный — **1** менеджер, у него сверх лимита ≈ **17,2 млн руб.**; «внимание» — 1 менеджер. Узнайте по `employees`, что с ним стало.

### Задание А2. Функция `fn_invoice_penalty(p_invoice_id, p_date, p_rate_per_day)`

Пеня = непогашенный остаток счёта на дату × ставка (% в день) / 100 × дни просрочки (`p_date − due_date`).

Требования:
* `p_date` по умолчанию `DATE '2025-12-31'`, при `NULL` — тоже дата среза;
* `p_rate_per_day` по умолчанию `0.1`; если `NULL`, < 0 или > 1 — `RAISE EXCEPTION ... USING ERRCODE = 'invalid_parameter_value', HINT = '...'`;
* `p_invoice_id IS NULL` — ошибка `null_value_not_allowed`; счёт не найден — ошибка `no_data_found`;
* оплачен полностью или не просрочен — вернуть `0`;
* `LANGUAGE plpgsql STABLE`, результат округлить до копеек.

*Подсказки:* `v_inv pitanie.invoices%ROWTYPE`; `SELECT * INTO v_inv ...; IF NOT FOUND THEN ...`; разность дат в PostgreSQL — целое число дней.

**Проверка:**
* `fn_invoice_penalty(1)` → `0` (счёт оплачен);
* `fn_invoice_penalty(2045)` → **66 261,62**; с `p_date => NULL` — то же; на `2025-01-15` → `0`; со ставкой `0.05` → **33 130,81**;
* `fn_invoice_penalty(2045, DATE '2025-12-31', -1)` → ошибка с подсказкой (пометьте `-- ОЖИДАЕМАЯ ОШИБКА`).

Затем посчитайте пени **по всем клиентам** и выведите топ-3. У какого клиента 39 просроченных счетов и сколько пени не предъявлено? *(≈ 846 тыс. руб.)*

### Задание А3. Цикл по месяцам 2025: выручка против плана

`FOR m IN 1..12 LOOP`: для каждого месяца — факт выручки, план (сумма `sales_plan` по всем категориям), отклонение в %, **нарастающий** процент выполнения и метка:
`▼ провал` (отклонение < −10 %), `▽ ниже плана` (< 0), `▲ план выполнен`.

*Подсказки:* начало месяца — `make_date(2025, m, 1)`; условие периода `>= начало AND < начало + INTERVAL '1 month'`; накопительные суммы — переменные `v_cum_fact`, `v_cum_plan`.

**Проверка:** 12 строк; за год выполнение **93,2 %**; «провал» — в двух месяцах второго полугодия. Отдельным запросом определите, **какая категория** даёт основной вклад в отклонение второго полугодия.

### Задание А4. Устойчивость к ошибкам

* в конце выведите число успешных расчётов и обработанных ошибок.

**Проверка:** `Успешно: 3, ошибок обработано: 3`; блок завершается без ошибки.

## Вариант 2 — Команда Б «Производство и закупки»

> **Контекст.** Директор по производству хочет каждое утро получать «светофор» по линиям и поставщикам, а главный механик — оценку стоимости простоев по своим заявкам. Ошибочные заявки не должны ломать расчёт — их нужно записывать в журнал.

### Задание Б1. DO-блок «Светофор линий» (OEE-подобный показатель, 2025 г.)

Для каждой линии (цикл `FOR r IN SELECT ...`) рассчитайте:

| Показатель | Формула |
|---|---|
| Доступность A | `1 − часы закрытых простоев / (число смен × 12 ч)` |
| Производительность P | `выпуск / план` |
| Качество Q | `1 − брак / выпуск` |
| OEE | `A × P × Q` |

Класс: `норма` (OEE ≥ 95 %), `внимание` (≥ 90 %), `КРИТИЧНО` (< 90 %); если OEE не определён — `нет данных`. Используйте `IF / ELSIF / ELSE`, константу `c_shift_hours`.

*Подсказки:* часы простоя считайте отдельным `SELECT ... INTO v_hours` внутри цикла (`EXTRACT(EPOCH FROM end_time − start_time) / 3600`); деление — через `NULLIF`.

**Проверка:** 5 строк; одна линия — `КРИТИЧНО` с OEE ≈ **81,5 %** (у неё хуже **все три** компонента); одна — `внимание` из-за качества (Q ≈ 0,953). Какие это линии?

### Задание Б2. Функция `fn_downtime_cost(p_line_id, p_hours)`

Стоимость простоя = часы × `capacity_per_hour` × средняя маржа единицы продукции линии в 2025 г. (`base_price − standard_cost`, взвешенно по выпуску).

Проверки (`RAISE EXCEPTION ... USING ERRCODE, DETAIL, HINT`):
* `NULL` в любом параметре → `null_value_not_allowed`;
* `p_hours < 0` или `> 8784` → `invalid_parameter_value`, HINT «проверьте единицы измерения»;
* линии нет → ошибка с подсказкой, где посмотреть список линий.

Используйте `v_capacity pitanie.production_lines.capacity_per_hour%TYPE`.

**Проверка:**
* стоимость 1 часа: линия 1 — **257 736,82**, линия 2 — **41 570,86** руб.;
* `fn_downtime_cost(2, 590.07)` → ≈ **24,53 млн** (сравните с оценкой из лабораторной модуля 9);
* `fn_downtime_cost(2, -3)` и `fn_downtime_cost(9, 10)` → понятные ошибки (`-- ОЖИДАЕМАЯ ОШИБКА`).

### Задание Б3. Цикл по поставщикам: переплата к лучшей цене

Вложенные циклы: внешний — по поставщикам, внутренний — по материалам поставщика (средневзвешенная цена). Для каждого материала найдите лучшую среднюю цену среди всех поставщиков (`SELECT MIN(...) INTO v_best`), переплату `qty × (avg_price − v_best)`. Материалы с лучшей ценой пропускайте (`CONTINUE WHEN`). Выведите поставщиков с переплатой > 0, пометив `← ПРОВЕРИТЬ` тех, у кого переплата > 1 млн; в конце — общий итог.

**Проверка:** **4** поставщика с переплатой, общий итог ≈ **4,53 млн**; помечен один поставщик (≈ 3,93 млн). Сравните с результатом `v_supplier_price_benchmark` из модуля 9 — цифры должны совпасть.

### Задание Б4. Динамический SQL: профиль столбца

2. Проверка существования столбца по `information_schema.columns`.
3. `RETURN QUERY EXECUTE format('SELECT ... COUNT(%I) ... FROM pitanie.%I', ...)`.

**Проверка:**
* `('equipment_downtime', 'end_time')` → 282 строки, **4** NULL — что это означает для расчёта простоев?

### Задание Б5. Журнал ошибок
