Сегодня: подзапросы внутри шагов 1, 2, 6 (и 4)Подзапрос — это полноценный SELECT со своим конвейером шагов 1…9, вложенный в шаг внешнего запроса: в FROM — как производная таблица, в WHERE/HAVING — как условие (IN, EXISTS, сравнение), в SELECT — как скалярное значение. Коррелированный подзапрос вычисляется для каждой строки внешнего.
Вопрос аудитории: в каком месте запроса подзапрос может вернуть таблицу, а в каком — только одно значение? Обсудить по схеме.

С чего начнём

Финансовый директор просит: «Покажите позиции, где скидка выше средней по компании».

  • Как бы вы решили это с помощью уже известных инструментов (модули 1–4)?
  • Сколько запросов придётся выполнить? Что будет, если завтра средняя изменится?
  • А если нужно «выше средней по своему менеджеру»?
⏱ 3 мин
Ожидаемые ответы: два запроса — сначала AVG, потом подставить число руками (хрупко, значение «зашито»); можно CROSS JOIN с агрегатом (решение из модуля 4). Для «своего менеджера» — JOIN с производной таблицей по группам. Подводим: подзапрос делает это одним запросом, а коррелированный — «для своей группы».

Виды подзапросов. Некоррелированные подзапросы

Подзапрос вычисляется один раз — результат подставляется во внешний запрос

Классификация подзапросов

СинтаксисПодзапрос всегда в скобках. Производной таблице в FROM даём псевдоним (в PostgreSQL 16 он стал необязательным, но в других СУБД обязателен).

Схема: некоррелированный подзапрос выполняется один раз

SELECT product_name, base_price FROM products WHERE base_price > (SELECT AVG(base_price) -- ① выполняется один раз FROM products) -- ② → 150.06 ORDER BY base_price DESC; -- ③ 9 строк из 35
Как читать схемуПодсвечен подзапрос. Номера в комментариях — шаги на схеме: ① подзапрос считается один раз, ② его результат подставляется как константа, ③ внешний запрос фильтрует строки.

Скалярный подзапрос в WHERE


-- средняя скидка по компании
SELECT ROUND(AVG(discount_pct), 2)
FROM   order_items;             -- 7.25

-- позиции со скидкой выше средней
SELECT COUNT(*) AS items_above_avg
FROM   order_items
WHERE  discount_pct >
       (SELECT AVG(discount_pct)
        FROM   order_items);    -- 5 483
Что происходитPostgreSQL вычисляет подзапрос один раз (в плане — InitPlan) и сравнивает каждую строку с готовым числом.
Почему не WHERE discount_pct > AVG(discount_pct)?Агрегаты в WHERE запрещены: WHERE отбирает строки до группировки.

Скалярный подзапрос в SELECT и его ограничения


SELECT product_name,
       base_price,
       ROUND(100.0 * base_price / (SELECT MAX(base_price) FROM products), 1) AS pct_of_max
FROM   products
ORDER  BY base_price DESC
LIMIT  3;          -- Сыр Гауда 100.0 · Сыр Российский 88.5 · Конфеты ассорти 38.3
  

-- ОЖИДАЕМАЯ ОШИБКА: в категории 13 пять продуктов
SELECT product_name,
       (SELECT base_price
        FROM   products
        WHERE  category_id = 13) AS cheese_price
FROM   products;
-- ERROR: more than one row returned
--        by a subquery used as an expression
      

-- ИСПРАВЛЕНИЕ: ORDER BY + LIMIT 1 → ровно одна строка
SELECT product_name,
       base_price,
       (SELECT product_name
        FROM   products
        WHERE  category_id = 13
        ORDER  BY base_price DESC
        LIMIT  1) AS top_cheese
FROM   products
WHERE  category_id = 32;
-- Соус сырный 200 г             129 · Сыр Гауда 45% 1 кг
-- Соус сливочно-чесночный 200 г 119 · Сыр Гауда 45% 1 кг
ПравилоСкалярный подзапрос должен вернуть 1 строку × 1 столбец: ≥ 2 строк — ошибка, 0 строк — NULL. Как гарантировать одну строку: агрегат (MAX, SUM…) или ORDER BY … LIMIT 1 — он нужен, когда требуется не число, а значение из «строки-лидера» (имя, дата), которое агрегатом не получить.
LIMIT без ORDER BY — лотереяLIMIT 1 без сортировки вернёт произвольную строку, а при равных ценах результат тоже не определён — добавьте второй ключ сортировки. И не прячьте LIMIT 1-ом ошибку в логике: если строк «не должно быть» несколько, разберитесь, откуда они.
Если подзапрос стоит в WHERE и должен вернуть несколько значений, это уже не скалярный, а многострочный подзапрос: вместо «=» нужен IN / ANY / ALL — это следующий слайд. В SELECT многострочный подзапрос использовать нельзя: в ячейку результата помещается только одно значение.

Квиз: пустой скалярный подзапрос

Что вернёт запрос, если у клиента 73 нет ни одного заказа?


SELECT customer_name,
       (SELECT MAX(order_date) FROM orders WHERE customer_id = 73) AS last_order
FROM   customers
WHERE  customer_id = 73;
  • Ошибку: подзапрос вернул 0 строк
  • 0 строк — клиент отфильтруется
  • 1 строку: «ООО "Новый горизонт"», last_order = NULL
  • 1 строку с датой 0001-01-01

MAX по пустому набору — NULL; скалярный подзапрос без строк тоже даёт NULL. Внешняя строка сохраняется.

Многострочный подзапрос: IN, ANY / SOME, ALL


-- клиенты Сибирского ФО
SELECT customer_name, customer_type
FROM   customers
WHERE  region_id IN
       (SELECT region_id
        FROM   regions
        WHERE  federal_district = 'Сибирский');
-- 15 строк

-- дороже ЛЮБОГО печенья и вафель
SELECT product_name, base_price
FROM   products
WHERE  base_price > ALL
       (SELECT base_price
        FROM   products
        WHERE  category_id = 21);
-- 15 строк, от 112 руб.
ЗаписьСмысл
= ANY (…)то же, что IN
> ANY (…)больше хотя бы одного (≈ > MIN)
> ALL (…)больше всех (≈ > MAX)
= ALL (…)равно каждому: TRUE, только если все значения набора одинаковы и равны проверяемому (на пустом наборе — TRUE)
<> ALL (…)то же, что NOT IN
SOMEсиноним ANY
«≈» — не случайноЭквивалентность с MIN/MAX нарушается на пустом наборе и при NULL.

02

Коррелированные подзапросы

«Для каждой строки внешнего запроса вычислить показатель её группы»

Как «думает» коррелированный подзапрос


SELECT p.product_name, p.category_id, p.base_price
FROM   products AS p                                   -- ① берём очередную строку p
WHERE  p.base_price > (SELECT AVG(p2.base_price)          -- ② считаем среднее…
                       FROM   products AS p2
                       WHERE  p2.category_id = p.category_id)  -- …только для её категории
ORDER  BY p.category_id, p.base_price DESC;           -- ③ сравниваем, повторяем · 14 строк

Логически

подзапрос выполняется для каждой строки внешнего запроса (35 раз)

Физически

оптимизатор может кэшировать, превратить в JOIN (Semi/Anti Join) или использовать индекс

Обязательно

разные псевдонимы p и p2, иначе корреляция «пропадёт»

Схема: коррелированный подзапрос — для каждой строки

SELECT p.product_name, p.category_id, p.base_price FROM products AS p -- внешний: строка за строкой WHERE p.base_price > (SELECT AVG(p2.base_price) FROM products AS p2 WHERE p2.category_id = p.category_id) -- связь ORDER BY p.category_id, p.base_price DESC; -- 14 строк

EXISTS и NOT EXISTS

Полусоединение и антисоединение: важен факт наличия строки, а не её значения

EXISTS — полусоединение (semi join)


-- клиенты, у которых были возвраты «Истёк срок годности»
SELECT c.customer_name, r.region_name
FROM   customers AS c
LEFT   JOIN regions AS r ON r.region_id = c.region_id
WHERE  EXISTS (SELECT 1
               FROM   orders  AS o
               JOIN   returns AS rt ON rt.order_id = o.order_id
               WHERE  o.customer_id = c.customer_id
                 AND  rt.reason = 'Истёк срок годности')
ORDER  BY r.region_name, c.customer_name;
-- 37 клиентов; больше всего — Новосибирская обл. и Красноярский край
  • EXISTS = TRUE, если подзапрос вернул хотя бы одну строку
  • список SELECT неважен: SELECT 1, SELECT *, SELECT NULL — одно и то же
  • строки внешней таблицы не размножаются (в отличие от JOIN)
  • поиск останавливается на первой найденной строке
  • результат — только TRUE / FALSE, никогда не UNKNOWN

NOT EXISTS — антисоединение (anti join)

FROM   customers AS c
WHERE  NOT EXISTS (SELECT 1
                   FROM   orders AS o
                   WHERE  o.customer_id = c.customer_id
                     AND  o.order_date >= DATE '2025-10-01');

Квиз: выберите лучший инструмент

Нужно найти материалы, которые ни разу не списывались. В material_writeoffs.material_id NULL быть не может (NOT NULL). Какой вариант надёжнее всего на будущее?

  • WHERE material_id NOT IN (SELECT material_id FROM material_writeoffs)
  • WHERE NOT EXISTS (SELECT 1 FROM material_writeoffs w WHERE w.material_id = m.material_id)
  • JOIN material_writeoffs w ON w.material_id <> m.material_id
  • WHERE material_id <> ANY (SELECT material_id FROM material_writeoffs)

Сегодня NOT IN тоже сработает, но NOT EXISTS не зависит от NULL и даёт Anti Join. JOIN с <> размножает строки, а <> ANY истинно почти всегда.

Что запомнить

  • Скалярный подзапрос: ≥ 2 строк — ошибка, 0 строк — NULL
  • ALL на пустом наборе — TRUE; на наборе с NULL — не TRUE
  • Коррелированный подзапрос = «показатель своей группы»; следите за псевдонимами
  • NOT IN + NULL = пустой результат. По умолчанию — NOT EXISTS
  • EXISTS/NOT EXISTS превращаются в Semi/Anti Join — это быстро
  • JOIN — когда нужны столбцы и агрегаты второй таблицы; EXISTS — когда нужен только факт
