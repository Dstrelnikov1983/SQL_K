Цепочка CTE: план / факт 2025


WITH fact AS (                                   -- шаг 1: факт по месяцам и категориям
    SELECT EXTRACT(MONTH FROM o.order_date)::int AS m,
           pc.parent_category_id                 AS top_cat,
           SUM(oi.quantity * oi.unit_price * (1 - oi.discount_pct / 100)) AS fact_amount
    FROM   pitanie.orders             AS o
    JOIN   pitanie.order_items        AS oi ON oi.order_id    = o.order_id
    JOIN   pitanie.products           AS p  ON p.product_id   = oi.product_id
    JOIN   pitanie.product_categories AS pc ON pc.category_id = p.category_id
    WHERE  o.status <> 'Отменён'
      AND  o.order_date >= DATE '2025-01-01' AND o.order_date < DATE '2026-01-01'
    GROUP  BY 1, 2
),
plan AS (                                        -- шаг 2: план
    SELECT plan_month AS m, category_id AS top_cat, plan_amount
    FROM   pitanie.sales_plan
    WHERE  plan_year = 2025
),
pf AS (                                          -- шаг 3: соединяем по полугодиям
    SELECT pl.top_cat,
           CASE WHEN pl.m <= 6 THEN 'H1' ELSE 'H2' END AS half,
           SUM(pl.plan_amount)             AS plan_amount,
           SUM(COALESCE(f.fact_amount, 0)) AS fact_amount
    FROM   plan AS pl
    LEFT   JOIN fact AS f ON f.m = pl.m AND f.top_cat = pl.top_cat
    GROUP  BY 1, 2
)
SELECT c.category_name, pf.half,
       ROUND(100 * pf.fact_amount / pf.plan_amount, 1) AS done_pct
FROM   pf
JOIN   pitanie.product_categories AS c ON c.category_id = pf.top_cat
ORDER  BY c.category_id, pf.half;
Обратить внимание: каждое следующее CTE ссылается на предыдущие; LEFT JOIN от плана, чтобы не потерять месяцы без продаж.

Квиз: область видимости CTE

Запрос: WITH a AS (SELECT ...), b AS (SELECT ... FROM a) SELECT ... FROM b;
Следующим оператором выполняем SELECT * FROM a;. Что произойдёт?

  • Вернутся строки CTE a — оно сохранилось в сессии
  • Вернутся строки, если CTE было MATERIALIZED
  • Ошибка relation "a" does not exist
  • Вернутся строки CTE b

CTE живёт только в пределах одного оператора. Чтобы «сохранить» запрос — представление; чтобы сохранить данные — таблица или материализованное представление; чтобы сохранить данные на время работы — временная таблица.

Как работает WITH RECURSIVE


WITH RECURSIVE имя AS (
    -- 1. якорь: стартовые строки
    SELECT ...
    FROM   таблица
    WHERE  условие_старта
    UNION ALL
    -- 2. рекурсивная часть:
    --    ссылается на само CTE
    SELECT ...
    FROM   таблица AS t
    JOIN   имя ON t.parent = имя.id
)
SELECT * FROM имя;
  1. Выполняется якорь → «рабочая таблица» (шаг 0).
  2. Рекурсивная часть выполняется только для строк предыдущего шага → шаг 1, 2…
  3. Остановка — когда очередной шаг вернул 0 строк.
  4. Результат — UNION ALL всех шагов.
ОпасностьЦикл в данных (A → B → A) = бесконечная рекурсия. Страховка: ограничение глубины WHERE lvl < 10 или CYCLE id SET is_cycle USING path (PG 14+).

Схема по шагам: подчинённые финансового директора Беловой М. С. — якорь WHERE employee_id = 2, рекурсия JOIN имя ON e.manager_id = имя.employee_id

Что не так? 2 мин

ОтветБез RECURSIVE CTE не видит само себя — имя org внутри его тела ещё не существует. В PostgreSQL ключевое слово обязательно.
Правила
  • RECURSIVE пишется один раз после WITH и действует на весь блок
  • В блоке WITH RECURSIVE могут быть и обычные CTE
  • С RECURSIVE CTE могут ссылаться друг на друга независимо от порядка объявления
Показать запрос, дать 1–2 минуты подумать. Типичные версии слушателей: «не та таблица», «нужен UNION, а не UNION ALL», «нет условия остановки». Правильный ответ — отсутствует RECURSIVE. Можно выполнить запрос вживую и показать ошибку. Затем перейти к сравнению СУБД: кто работал с SQL Server/Oracle, мог привыкнуть писать без RECURSIVE.

RECURSIVE в разных СУБД

СУБДКлючевое слово RECURSIVEСинтаксис
PostgreSQL (Yandex Managed)обязательноWITH RECURSIVE t AS (…)
MySQL 8.0+, MariaDB 10.2+обязательноWITH RECURSIVE t AS (…)
Стандарт SQL:1999обязательноWITH RECURSIVE t AS (…)
SQLiteнеобязательноWITH [RECURSIVE] t AS (…)
MS SQL Serverне используется — синтаксическая ошибкаWITH t AS (…)
Oracle 11gR2+не используетсяWITH t (col1, col2) AS (…)
SQL Server, OracleРекурсия распознаётся автоматически по ссылке CTE на само себя. В Oracle для рекурсивного CTE обязателен список столбцов; есть и старый синтаксис CONNECT BY.
Практический выводПереносите запрос между СУБД — проверьте RECURSIVE первым делом. Логика «якорь + UNION ALL + рекурсивная часть» везде одинакова.
Спросить: кто работал с другими СУБД? Ограничение глубины тоже различается: в SQL Server по умолчанию MAXRECURSION 100 (OPTION (MAXRECURSION n)), в MySQL — cte_max_recursion_depth = 1000, в PostgreSQL встроенного лимита нет — защищаемся условием на глубину или CYCLE.

WITH RECURSIVE org AS (
    SELECT employee_id, full_name, manager_id,
           1                AS lvl,
           full_name::text  AS path
    FROM   pitanie.employees
    WHERE  manager_id IS NULL
    UNION ALL
    SELECT e.employee_id, e.full_name, e.manager_id,
           org.lvl + 1,
           org.path || ' → '
                    || split_part(e.full_name, ' ', 1)
    FROM   pitanie.employees AS e
    JOIN   org ON e.manager_id = org.employee_id
)
SELECT repeat('    ', lvl - 1) || full_name AS tree,
       lvl
FROM   org
ORDER  BY path;

WITH RECURSIVE team AS (
    SELECT employee_id, full_name, 0 AS depth
    FROM   pitanie.employees

),
rev AS (
    SELECT o.employee_id,
           SUM(oi.quantity * oi.unit_price
               * (1 - oi.discount_pct / 100)) AS revenue,

ORDER  BY t.depth, revenue_mln DESC;

CREATE OR REPLACE FUNCTION stud_ivanov.fn_customer_orders(
    p_customer_id integer,
    p_from        date DEFAULT DATE '2024-01-01',
    p_to          date DEFAULT DATE '2025-12-31'
)
RETURNS TABLE (
    order_id     integer,
    order_number varchar,
    order_date   date,
    status       varchar,
    net_amount   numeric
)
LANGUAGE sql
STABLE
AS $$
    SELECT o.order_id, o.order_number, o.order_date, o.status,
           ROUND(SUM(oi.quantity * oi.unit_price
                     * (1 - oi.discount_pct / 100)), 2)
    FROM   pitanie.orders      AS o
    JOIN   pitanie.order_items AS oi ON oi.order_id = o.order_id
    WHERE  o.customer_id = p_customer_id
      AND  o.order_date BETWEEN p_from AND p_to
    GROUP  BY o.order_id, o.order_number, o.order_date, o.status
    ORDER  BY o.order_date
$$;

LANGUAGE sql — тело = один запрос


CREATE OR REPLACE FUNCTION stud_ivanov.fn_line_defects_sql(
    p_line_id integer, p_day date)
RETURNS TABLE (batch_number varchar, shift varchar,
               produced_qty integer, defect_qty integer,
               defect_pct numeric)
LANGUAGE sql
STABLE
AS $$
    SELECT b.batch_number, b.shift, b.produced_qty, b.defect_qty,
           ROUND(100.0 * b.defect_qty / b.produced_qty, 2)
    FROM   pitanie.production_batches AS b
    WHERE  b.line_id = p_line_id
      AND  b.production_date = p_day
    ORDER  BY b.shift
$$;
  

EXPLAIN → Index Scan using ix_batches_date …   -- встроена в запрос

LANGUAGE plpgsql — блок кода: переменные, IF, циклы


CREATE OR REPLACE FUNCTION stud_ivanov.fn_line_defects_pl(
    p_line_id integer, p_day date)
RETURNS TABLE (batch_number varchar, shift varchar,
               produced_qty integer, defect_qty integer,
               defect_pct numeric)
LANGUAGE plpgsql
STABLE
AS $$
BEGIN
    IF p_day > CURRENT_DATE THEN                -- проверка параметра
        RAISE EXCEPTION 'Дата % ещё не наступила', p_day;
    END IF;

    RETURN QUERY                                -- вернуть строки запроса
    SELECT b.batch_number, b.shift, b.produced_qty, b.defect_qty,
           ROUND(100.0 * b.defect_qty / b.produced_qty, 2)
    FROM   pitanie.production_batches AS b
    WHERE  b.line_id = p_line_id
      AND  b.production_date = p_day
    ORDER  BY b.shift;
END;
$$;
  

EXPLAIN → Function Scan on fn_line_defects_pl   -- «чёрный ящик»
Результат одинаковыйSELECT * FROM …(3, DATE '2025-06-10') → П250610-3Д: 1407 / 20 шт. (1,42 %), П250610-3Н: 1314 / 118 шт. (8,98 %). SQL — когда хватает одного запроса; PL/pgSQL — когда нужны проверки, ветвления, несколько шагов (подробно — модуль 10).
Ловушка PL/pgSQLСтолбцы из RETURNS TABLE — это переменные функции. Без алиаса SELECT shift … → column reference "shift" is ambiguous. Всегда пишите b.shift.
Обе функции проверены на стенде (создавались в pg_temp). Вопрос группе: какую версию выбрать для витрины, которую BI вызывает с фильтрами? (SQL — встраивается, фильтры и индексы работают; PL/pgSQL выполняется целиком и возвращает весь набор). Вопрос 2: зачем тогда PL/pgSQL? (валидация параметров, сообщения об ошибках, многошаговая логика, временные таблицы внутри). Связь со слайдом T-SQL: SQL-функция ≈ inline TVF, PL/pgSQL ≈ multi-statement TVF.

Итоги: что запомнить

CTE

  • Шаги запроса сверху вниз
  • Живёт один оператор
  • RECURSIVE: якорь + UNION ALL + рекурсивная часть
  • MATERIALIZED — барьер оптимизации

Представления

  • Единая формула — один источник истины
  • Простые — обновляемые; WITH CHECK OPTION
  • Скрывают столбцы/строки
  • MV хранит данные, нужен REFRESH

Табличные функции

  • Представление с параметрами
  • LANGUAGE sql + STABLE → встраивание
  • Вызов во FROM и через LATERAL
  • Изменили RETURNS — DROP + CREATE

Проверьте себяПочему функцию, читающую таблицы, нельзя объявлять IMMUTABLE?
Ответ: IMMUTABLE-результат может быть закэширован/вычислен на этапе планирования и использован в индексах — при изменении данных получим неверные результаты.
