# Модуль 12. Лабораторная работа «Процедуры, которые закрывают дыры в деньгах»

**Цель:** упаковать найденные в курсе проверки и бизнес-операции «Питание +» в параметризованные
хранимые процедуры PostgreSQL: с валидацией входных данных, понятными ошибками, транзакционной
целостностью, возвратом результата через `INOUT`, и подготовить их к промышленному использованию
(права, исходный код, отладка).

**Время:** 60 минут (+ процедуры становятся частью итогового SQL-пакета — см. `final_project.md`).

**Формат:** в группах по 2–3 человека внутри команды; каждая группа пишет все 4 процедуры своего
варианта, внутри группы можно распределить процедуры между участниками.

## Вариант 1 — Команда А «Финансы и продажи»

### Задание А1. `sp_apply_payment` — проведение оплаты (12 мин)

Сигнатура:

```sql
sp_apply_payment(p_invoice integer, p_amount numeric,
                 p_date date DEFAULT current_date,
                 p_method varchar DEFAULT 'Банковский перевод',
                 INOUT p_balance numeric DEFAULT NULL)
```

Шаги:

1. Сумма > 0, способ оплаты — `Банковский перевод` или `Взаимозачёт`.
2. Захватить счёт `SELECT … INTO … FOR UPDATE`; если не найден — ошибка `no_data_found`.
3. Дата оплаты не раньше даты счёта.
4. Сумма не превышает остаток (`fn_invoice_balance`) — иначе `check_violation` с остатком в тексте и `HINT`.
5. Вставить оплату, вернуть в `p_balance` новый остаток.
6. `NOTICE`, если оплата просрочена (на сколько дней) и если счёт закрыт полностью.

**Проверка:**
* `CALL sp_apply_payment(4070, 50000, DATE '2025-12-25');` → `p_balance = 28290.05`;
* повтор на 40 000 → ошибка «Переплата… остаток 28290.05»;
* полная оплата счёта 2031 датой `2025-12-30` (используйте именованные параметры) →
  `NOTICE … просрочкой 333 дн.`, `p_balance = 0.00`.

### Задание А2. `sp_close_month` — закрытие месяца (15 мин)

`sp_close_month(p_year integer, p_month integer)` формирует в `month_close_report` строки по каждому
каналу продаж (выручка, себестоимость по `standard_cost`, маржа, маржа %) и строку `'Всего'`
с дебиторской задолженностью **на конец месяца** (счета до конца месяца минус оплаты до конца месяца)
и её просроченной частью (`due_date` раньше конца месяца).

Подсказки:

* период: `v_start := make_date(p_year, p_month, 1)`, `v_end := v_start + INTERVAL '1 month'`;
* отменённые заказы не учитывать;
* идемпотентность — `DELETE` строк периода перед `INSERT`;
* после формирования — `COMMIT` внутри процедуры (месяц «закрыт»);
* проверки: месяц 1..12, за период есть заказы.

**Проверка:** `CALL sp_close_month(2025, 12);` → 5 строк (4 канала + «Всего»); «Всего»: выручка
44 674 535,61, маржа 29,49 %, дебиторка 55 718 306,95, из неё просрочено 13 614 609,87.
Повторный вызов не создаёт дублей; `sp_close_month(2025, 13)` — ошибка.

**★** Закройте все 12 месяцев 2025 г. одним блоком `DO` с циклом `CALL` и найдите месяц с самой
низкой выручкой и месяц с самой высокой просроченной дебиторкой. Как менялась дебиторка в течение года?

### Задание А3. `sp_block_overdue_customers` — стоп-лист должников (12 мин)

```sql
sp_block_overdue_customers(p_days integer, p_limit_ratio numeric,
                           INOUT p_count integer DEFAULT NULL,
                           p_as_of date DEFAULT DATE '2025-12-31')
```

Блокирует (`customers.is_blocked = TRUE`, `blocked_at`, `blocked_reason`) клиентов, у которых
**одновременно** есть долг, просроченный более чем на `p_days` дней, **и** общий долг больше
`p_limit_ratio × credit_limit`. Каждую блокировку записать в `customer_block_log`. Уже заблокированных
не трогать. Вернуть число заблокированных.

Подсказки: остаток счетов на дату `p_as_of` (оплаты до этой даты); цикл `FOR r IN <запрос> LOOP`;
порядок обработки по `customer_id`.

**Проверка:** `CALL sp_block_overdue_customers(30, 1.0, NULL);` → `p_count = 1`. Кто это и каков его долг?
Затем `(30, 0.5, NULL)` → ещё 1 клиент. Отрицательные пороги — ошибка.

### Задание Б1. `sp_register_batch` — регистрация партии и расход сырья (15 мин)

```sql
sp_register_batch(p_product_id integer, p_line_id integer, p_date date, p_shift varchar,
                  p_planned integer, p_produced integer,
                  p_defect integer DEFAULT 0, p_operator_id integer DEFAULT NULL,
                  INOUT p_batch_id integer DEFAULT NULL)
```

В **одной** транзакции:

1. Проверки: смена `День`/`Ночь`; количества неотрицательны, брак ≤ выпуск; у продукта есть рецептура;
   на линии в эту дату и смену ещё нет партии (одна партия = одна смена).
2. Номер партии `П<ГГММДД>-<линия><Д|Н>`, например `П260112-2Д`.
3. Вставить партию → `RETURNING batch_id INTO p_batch_id`.
4. Вставить расход сырья по рецептуре (`qty_per_unit × p_produced`) в `material_consumption`.
5. Уменьшить `material_stock`. Если сырья не хватает (сработает `CHECK (qty_on_hand >= 0)`),
   перехватить `check_violation` и выдать понятную ошибку со списком недостающих материалов —
   при этом **ни партия, ни расход не должны сохраниться**.

**Проверка:**
* `CALL sp_register_batch(13, 2, DATE '2026-01-12', 'День', 1500, 1450, 20, 53);` → `p_batch_id = 10001`,
  3 строки расхода, молочного жира списано 217.5 кг;
* повторный вызов → «Партия на линии 2 за 2026-01-12 (День) уже зарегистрирована»;
* ночная смена с выпуском 30 000 → «Недостаточно сырья: Молочный жир (нужно 4500.000, есть 3189.731)»,
  партий с `batch_id >= 10001` по-прежнему 1.

### Задание Б2. `sp_receive_delivery` — приёмка заказа поставщику (12 мин)

```sql
sp_receive_delivery(p_po_id integer, p_received_date date,
                    p_received_pct numeric DEFAULT 100,
                    p_quality varchar DEFAULT 'Принято',
                    INOUT p_items integer DEFAULT NULL)
```

Принимает все позиции заказа (`received_qty = quantity × p_received_pct / 100`), увеличивает остатки
(если не `Отклонено`), переводит заказ в `Получен`. Проверки: процент 0..100; допустимый статус
качества; заказ существует; заказ в статусе `Отправлен` (**повторная приёмка запрещена**);
дата приёмки не раньше даты заказа. `NOTICE` с опозданием относительно `expected_date`.

**Проверка:** `CALL sp_receive_delivery(945, DATE '2026-01-03');` → `p_items = 2`, опоздание 4 дн.;
повтор — ошибка; `(951, DATE '2026-01-02', 90, 'Принято частично')` → 2 позиции, опоздание 2 дн.

### Задание Б3. `sp_supplier_scorecard` — рейтинг поставщиков (15 мин)

```sql
sp_supplier_scorecard(p_year integer, INOUT p_rows integer DEFAULT NULL,
                      p_update_rating boolean DEFAULT TRUE)
```

Для каждого поставщика за год рассчитать и записать в `supplier_scorecard`:

| Показатель | Как считать |
|---|---|
| `price_index` | Σ(кол-во × цена) / Σ(кол-во × средняя цена этого материала у всех поставщиков за год) |
| `avg_delay` | среднее `GREATEST(received_date − expected_date, 0)` |
| `on_time_share` | доля позиций с `received_date <= expected_date` |
| `quality_share` | доля позиций со статусом `Принято` |
| `score` | `1 + 4 × (0.4 × ценовой балл + 0.3 × on_time + 0.3 × quality)`, ценовой балл = `(1.20 − price_index) / 0.35`, ограничить 0..1 |

Повторный запуск за год пересчитывает данные. При `p_update_rating` обновить `suppliers.rating`
(округлить до 0,1). Подсказка: средняя цена материала — оконная функция `AVG(...) OVER (PARTITION BY material_id)`.

**Проверка:** `CALL sp_supplier_scorecard(2025);` → `p_rows = 12`. Три поставщика с самым низким
`score` — кто они и что «тянет» их вниз? У кого самый высокий `price_index` и сколько он стоит
компании? Сравните новый рейтинг со старым (`pitanie.suppliers.rating`).

### Задание Б4. `sp_flag_lines_for_maintenance` — линии на ремонт / проверку (12 мин)

Для каждой линии за год: часы простоев (только закрытые простои, `end_time IS NOT NULL`) и за прошлый

план выполнен меньше чем на `p_plan_pct`. В колонку `reasons` записать все сработавшие причины

**Проверка:** `CALL sp_flag_lines_for_maintenance(2025);` → `p_flagged = 2`. Какие линии и по каким
причинам? При `p_downtime_growth => 3.0` у одной из линий остаётся только одна причина — какая?
