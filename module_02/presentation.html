Сегодня: выражения и функции — в SELECT (шаг 6) и WHERE (шаг 2)Типы, CAST, числовые и строковые функции, даты и CASE — это выражения. Чаще всего они вычисляются на шаге 6 SELECT и в условиях шага 2 WHERE. Помним: псевдоним из SELECT в WHERE ещё не существует — он появится только на шаге 6.
Показать общую схему курса: каждый модуль раскрывает один или несколько шагов. Вопрос аудитории: почему нельзя написать WHERE margin_pct > 10, если margin_pct — псевдоним из SELECT? (WHERE выполняется раньше SELECT.)

Разминка: что вернёт PostgreSQL?

SELECT 7 / 2;

  • 3.5
  • 3
  • 4
  • Ошибка: нужен CAST

integer / integer = integer, дробная часть отбрасывается (не округляется): -7 / 2 = -3. Чтобы получить 3.5: 7 / 2.0 или 7::numeric / 2. В T-SQL поведение такое же.

Спросить, кто ответил 3.5 — именно эта ошибка в модуле 1 «спрятала» долю брака. Мост к блоку о преобразованиях.

numeric против float


SELECT 0.1::float8 + 0.2::float8;
-- 0.30000000000000004

SELECT 0.1::float8 + 0.2::float8 = 0.3;
-- false (!)

SELECT 0.1::numeric + 0.2::numeric = 0.3;
-- true

SELECT 1234.5::numeric(5,2);
-- ОШИБКА: numeric field overflow
float — двоичная дробь0,1 нельзя точно записать в двоичной системе → накопление погрешности при суммировании тысяч строк.

numeric(10,2): всего 10 цифр, из них 2 после запятой → максимум 99 999 999,99.

Обсуждение: какой тип выбрать?

Вы — системный аналитик, проектируете новую таблицу «Рекламации клиентов». Какие типы вы зададите и почему?

  • ИНН клиента, телефон, почтовый индекс
  • сумма претензии, процент компенсации
  • дата и время поступления (филиалы в Москве и Новосибирске)
  • длительность рассмотрения
  • признак «решено в пользу клиента»
  • произвольные атрибуты от разных маркетплейсов
⏱ 5 мин
ИНН/телефон/индекс — varchar (ведущие нули, «+», не нужна арифметика) + CHECK формата; сумма — numeric(14,2); процент — numeric(5,2) с CHECK 0..100; время — timestamptz (разные пояса); длительность — interval (или вычислять); признак — boolean; атрибуты — jsonb. Подчеркнуть: тип — это часть требований, а не «деталь реализации».

CAST и ::, неявные преобразования, ошибки


SELECT CAST('2025-03-01' AS date),   -- стандарт SQL
       '2025-03-01'::date,           -- PostgreSQL
       CAST(189.567 AS numeric(10,2)), -- 189.57
       '42'::integer + 1;            -- 43

-- Неявно: литерал подстраивается под столбец
SELECT COUNT(*)                      -- 218
FROM   orders
WHERE  order_date >= '2025-12-01';
      

SELECT 'abc'::integer;
-- invalid input syntax for type integer
SELECT '2025-02-30'::date;
-- date/time field value out of range
SELECT 3000000000::integer;
-- integer out of range

Квиз: склейка с NULL

У поставщика 12 phone IS NULL. Что вернёт 'Тел.: ' || phone?

  • 'Тел.: '
  • 'Тел.: NULL'
  • NULL
  • Ошибку

Оператор || с NULL даёт NULL. CONCAT('Тел.: ', phone) вернёт 'Тел.: ' — CONCAT/CONCAT_WS пропускают NULL. В T-SQL + ведёт себя как || (при CONCAT_NULL_YIELDS_NULL ON).

Обсуждение: насколько можно доверять нормализации?

Нормализация названия склеила три «Ромашки», но «ИП Иванов (Колос)» и «ООО "Колос" (дубль)» остались разными. Дубли нашлись только по ИНН.

  • Какие ложные срабатывания даст сравнение только по названию? («ООО "Альфа"» в Москве и в Самаре)
  • Когда и ИНН не поможет? (филиалы, ИП → ООО, опечатки)
  • Кто в компании должен принимать решение «это один клиент» и как это зафиксировать в данных?
⏱ 5 мин
Ожидаемо: одинаковые названия у разных юрлиц; ИНН у филиалов один (нужен КПП), смена ОПФ меняет ИНН, опечатки в ИНН (проверка контрольной суммы). Решение — мастер-данные (MDM), владелец справочника, таблица соответствий «старый id → основной id». Найденные дубли искажают топ клиентов, кредитные лимиты (лимит выдаётся на каждую карточку!).

Кейс: «Сколько стоит масло, которое мы продаём?»


SELECT p.product_name,
       oi.unit_price,
       oi.discount_pct,
       ROUND(oi.unit_price
             * (1 - oi.discount_pct / 100), 2) AS net,
       p.standard_cost,
       ROUND(oi.unit_price
             * (1 - oi.discount_pct / 100)
             - p.standard_cost, 2)             AS margin
FROM   order_items AS oi
JOIN   orders      AS o ON o.order_id   = oi.order_id
JOIN   products    AS p ON p.product_id = oi.product_id
WHERE  oi.unit_price * (1 - oi.discount_pct / 100)
       < p.standard_cost
  AND  o.status <> 'Отменён'
  AND  o.order_date >= DATE '2025-03-01'
ORDER  BY margin;
