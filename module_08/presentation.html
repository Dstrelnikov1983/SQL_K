Сегодня: шаг 5 — оконные функцииОкна вычисляются после GROUP BY и HAVING, но до DISTINCT, ORDER BY и LIMIT. Поэтому окно «видит» уже отфильтрованные строки и готовые группы (можно SUM(SUM(x)) OVER ()), но фильтровать по окну в WHERE нельзя — только во внешнем запросе или CTE.
Вопрос аудитории: почему rank() OVER (...) нельзя использовать в WHERE, но можно в ORDER BY? Ответ — по номерам шагов на схеме. Подробно вернёмся к этому на слайде «Логический порядок».

Зачем окна: задача «доля от итога»

Без окна — подзапрос для итога:


SELECT r.region_name,
       count(*) AS returns_cnt,
       round(100.0 * count(*) /
             (SELECT count(*) FROM returns), 1)
                AS share_pct
FROM   returns   AS rt
JOIN   orders    AS o ON o.order_id = rt.order_id
JOIN   customers AS c ON c.customer_id = o.customer_id
LEFT   JOIN regions AS r ON r.region_id = c.region_id
GROUP  BY r.region_name;

С окном — итог «из того же результата»:


SELECT r.region_name,
       count(*) AS returns_cnt,
       round(100.0 * count(*) /
             sum(count(*)) OVER (), 1)
                AS share_pct
FROM   …
GROUP  BY r.region_name
ORDER  BY returns_cnt DESC;

Главная мысльОкно считает агрегат по «соседям» строки, но не схлопывает строки. Поэтому в одном SELECT видны и деталь (партия), и контекст (среднее по линии).

Цель блока — переучить читать изнутри OVER наружу. Данные реальные: 13 позиций приёмки сахара, муки и хлопьев за январь 2025.

① OVER — повесить бирку, а не высыпать в бункер

SELECT m.material_name, poi.received_date, poi.unit_price, round(avg(poi.unit_price) -- ⑤ лаборант OVER ( -- ① бирка PARTITION BY poi.material_id -- ② закрома ORDER BY poi.received_date, -- ③ лента poi.po_item_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW -- ④ окно ), 2) AS avg3_price FROM purchase_order_items AS poi JOIN raw_materials AS m USING (material_id) WHERE poi.material_id IN (4, 6, 7) -- сахар, мука, хлопья AND poi.received_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31' ORDER BY poi.material_id, poi.received_date, poi.po_item_id;
Что делает СУБДСлово OVER превращает обычный агрегат в оконный. Без него avg(unit_price) схлопнул бы строки: в 1 итог, а с GROUP BY — в 3. С OVER строки остаются, у каждой появляется новый столбец-бирка avg3_price.
Сколько строк вошло — столько и вышлоOVER () с пустыми скобками — окно на весь склад: все 13 мешков. Всё, что пишется внутри скобок (②–④), лишь сужает и упорядочивает это окно.
Вопрос: «Что выведет avg(unit_price) OVER () для каждой строки?» (одно и то же число — среднее по 13 мешкам). Метафора «открытого окна»: строка не выходит из своей комнаты, но через окно видит соседей. Спросите: какой бизнес-вопрос нельзя решить GROUP BY, но можно окном? (сравнить конкретную поставку со средней).

② PARTITION BY — разложить по закромам

SELECT m.material_name, poi.received_date, poi.unit_price, round(avg(poi.unit_price) -- ⑤ лаборант OVER ( -- ① бирка PARTITION BY poi.material_id -- ② закрома ORDER BY poi.received_date, -- ③ лента poi.po_item_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW -- ④ окно ), 2) AS avg3_price FROM purchase_order_items AS poi JOIN raw_materials AS m USING (material_id) WHERE poi.material_id IN (4, 6, 7) -- сахар, мука, хлопья AND poi.received_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31' ORDER BY poi.material_id, poi.received_date, poi.po_item_id;
Что делает СУБДДелит 13 строк на 3 раздела по material_id — как GROUP BY, но без схлопывания. Каждый закром обрабатывается отдельно: окно и функция никогда не заглядывают через перегородку. Делить можно по нескольким столбцам: PARTITION BY material_id, supplier_id.
Без PARTITION BY весь склад — один закромТогда в «среднюю цену сахара» попадут мука по 36 ₽ и хлопья по 44 ₽ — и сахар по 84 ₽ будет выглядеть дорогим. Ошибка тихая: запрос отработает без ошибок.
Вопрос: «Сколько закромов будет при PARTITION BY material_id, supplier_id?» (столько, сколько уникальных пар). Мини-задание: какой столбец взяли бы для разделов в команде А? (customer_id, region_id, category_id). Обратите внимание: порядок мешков в закроме пока случайный — это следующий шаг.

③ ORDER BY — поставить мешки в очередь на ленте

SELECT m.material_name, poi.received_date, poi.unit_price, round(avg(poi.unit_price) -- ⑤ лаборант OVER ( -- ① бирка PARTITION BY poi.material_id -- ② закрома ORDER BY poi.received_date, -- ③ лента poi.po_item_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW -- ④ окно ), 2) AS avg3_price FROM purchase_order_items AS poi JOIN raw_materials AS m USING (material_id) WHERE poi.material_id IN (4, 6, 7) -- сахар, мука, хлопья AND poi.received_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31' ORDER BY poi.material_id, poi.received_date, poi.po_item_id;
Что делает СУБДВнутри каждого закрома мешки встают на ленту по received_date, а при равной дате — по po_item_id (тай-брейкер). Номер на ленте — это и есть row_number(). Этот ORDER BY не сортирует результат — за итоговый порядок строк отвечает последний ORDER BY запроса.
ORDER BY меняет рамку по умолчаниюКак только в OVER появился ORDER BY, рамка по умолчанию — RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: «от начала ленты до меня и всех моих ровесников». Поэтому sum(x) OVER (ORDER BY d) даёт нарастающий итог, а не сумму раздела.
Покажите на муке: #1219 пришла раньше #1199 — порядок задаёт дата, а не номер позиции. Вопрос: «Что будет, если убрать po_item_id, а две поставки хлопьев пришли 17.01 одновременно?» (порядок между ними не определён — результат может меняться от запуска к запуску). Это мостик к RANGE на шаге ④.

④ ROWS — смотровое окно над лентой

SELECT m.material_name, poi.received_date, poi.unit_price, round(avg(poi.unit_price) -- ⑤ лаборант OVER ( -- ① бирка PARTITION BY poi.material_id -- ② закрома ORDER BY poi.received_date, -- ③ лента poi.po_item_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW -- ④ окно ), 2) AS avg3_price FROM purchase_order_items AS poi JOIN raw_materials AS m USING (material_id) WHERE poi.material_id IN (4, 6, 7) -- сахар, мука, хлопья AND poi.received_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31' ORDER BY poi.material_id, poi.received_date, poi.po_item_id;
Что делает СУБДДля каждого мешка вырезает рамку — кусок ленты вокруг него. 2 PRECEDING AND CURRENT ROW = окно на 3 мешка: два предыдущих + текущий. Окно едет вместе с текущей строкой и не выходит за свой закром. Границы: UNBOUNDED PRECEDING · n PRECEDING · CURRENT ROW · n FOLLOWING · UNBOUNDED FOLLOWING.
У первых мешков окно неполноеМешок 1 видит только себя, мешок 2 — двоих. Это всё ещё «среднее», но не по 3 поставкам. Нужна честная средняя по 3 поставкам — посчитайте count(*) с той же рамкой и во внешнем запросе оставьте строки, где он равен 3.
Кликайте по одному: окно сдвигается на мешок. Перед каждым кликом спрашивайте: «Какой мешок выйдет из окна, какой войдёт?» После 5-го клика: «А что будет у первого мешка сахара?» — окно не перескакивает из хлопьев в сахар, у сахара своя лента и своё окно.

④ ROWS или RANGE: окно по мешкам или по календарю

SELECT poi.po_item_id, poi.received_date, poi.received_qty, sum(poi.received_qty) OVER ( ORDER BY poi.received_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS by_rows, sum(poi.received_qty) OVER ( ORDER BY poi.received_date RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS by_range -- = рамка по умолчанию FROM purchase_order_items AS poi WHERE poi.material_id = 7 -- хлопья AND poi.received_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31' ORDER BY poi.received_date, poi.po_item_id;
Два способа мерить окноROWS считает мешки (физические строки). RANGE меряет значение ключа сортировки: все мешки с той же датой — «ровесники» и входят в окно вместе. Есть и третий — GROUPS: считает группы ровесников.

⑤ Функция — лаборант у окна пишет результат на бирку

SELECT m.material_name, poi.received_date, poi.unit_price, round(avg(poi.unit_price) -- ⑤ лаборант OVER ( -- ① бирка PARTITION BY poi.material_id -- ② закрома ORDER BY poi.received_date, -- ③ лента poi.po_item_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW -- ④ окно ), 2) AS avg3_price FROM purchase_order_items AS poi JOIN raw_materials AS m USING (material_id) WHERE poi.material_id IN (4, 6, 7) -- сахар, мука, хлопья AND poi.received_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31' ORDER BY poi.material_id, poi.received_date, poi.po_item_id;
Что делает СУБДДля текущей строки берёт строки рамки, применяет к ним avg(poi.unit_price) и записывает результат в текущую строку — столбец avg3_price. Затем рамка сдвигается, и всё повторяется для следующего мешка.

Квиз: какой шаг забыли?

Аналитик посчитал скользящую среднюю цену сахара, но в окно попали мешки муки и хлопьев. Какой части не хватает в OVER (…)?

  • ① пустые скобки OVER () вместо OVER (…)
  • ② PARTITION BY poi.material_id
  • ③ ORDER BY poi.received_date
  • ④ ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

Без закромов весь склад — один раздел, и смотровое окно видит соседние мешки любой культуры. ORDER BY и ROWS задают порядок и ширину окна, но не перегородки.

Где аналогия с элеватором ломается?

Любая аналогия неточна. Найдите, где SQL ведёт себя не так, как настоящий элеватор. 5 мин

  1. На элеваторе мешки лежат в физическом порядке. Есть ли «естественный порядок» строк в таблице?
    → Нет. Без ORDER BY внутри OVER порядок не определён, и row_number() выдаст случайную нумерацию.
  2. Можно ли одни и те же мешки одновременно разложить по закромам по-разному?
    → В SQL — да: несколько OVER с разными PARTITION BY в одном SELECT. Закрома виртуальные, физически ничего не двигается.
  3. Может ли лаборант выбросить «дорогой» мешок прямо у окна?
    → Нет: окна считаются после WHERE и HAVING. Отбраковка — во внешнем запросе (CTE).
  4. У первых мешков окно неполное. Это ошибка или особенность? Чем это опасно для отчёта руководству?
    → Особенность: «среднее по 1 поставке» выглядит как скользящая средняя, но ей не является. Помечайте или отсекайте такие строки (count(*) OVER (…) = 3).
Работа в парах: 3 минуты на обсуждение, затем по одному ответу от пары. Ответы открывайте кликами. Хороший дополнительный вопрос: «Придумайте свою аналогию для оконной функции из вашей предметной области».

Рейтинг для премии: RANK, DENSE_RANK или ROW_NUMBER?

Директор по продажам хочет премировать «тройку лучших менеджеров квартала» по выручке. У двух менеджеров выручка совпала до рубля.

  • Какую функцию выбрать, чтобы решение было справедливым и воспроизводимым?
  • Достаточно ли выручки как метрики? (Вспомните скидки Соколова — 18 % при норме 10 %.)
⏱ 4 мин
RANK ≤ 3 при равных значениях на 2–3 месте — 3 или 4 человека; DENSE_RANK ≤ 3 — может быть больше трёх (все с 3-м значением); ROW_NUMBER — ровно 3, но кто третий — случайно, если нет второго ключа. Схема: ROWS, RANGE и GROUPS на одних данных

SELECT production_date, shift, produced_qty, sum(produced_qty) OVER ( ORDER BY production_date, shift ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS rows_1, -- ① sum(produced_qty) OVER ( ORDER BY production_date RANGE BETWEEN INTERVAL '1 day' PRECEDING AND CURRENT ROW) AS range_1d, -- ② sum(produced_qty) OVER ( ORDER BY production_date GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW) AS groups_1 -- ③ FROM production_batches WHERE line_id = 1 AND production_date BETWEEN DATE '2025-02-28' AND DATE '2025-03-04' ORDER BY production_date, shift;
Одна и та же «1 PRECEDING» — три разных ответаROWS — сколько строк, RANGE — насколько отличается значение ключа, GROUPS — сколько разных значений ключа. Для RANGE и GROUPS строки с той же датой — одна неразрывная группа.

Квиз: рамка по умолчанию

Какая рамка применяется в sum(amount) OVER (PARTITION BY customer_id ORDER BY invoice_date)?

  • ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  • RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  • ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  • Вся секция (PARTITION) целиком

С ORDER BY — RANGE до текущей строки включительно, с пирами: два счёта одного дня получат одинаковый итог. Без ORDER BY — вся секция.

7 смен или 7 дней?

Начальник цеха просит «график брака Линии 3 со сглаживанием за неделю». Линия работает в две смены, по воскресеньям стоит, иногда смена пропускается из-за простоя.

SELECT cat_id, month,
       round(revenue / 1e6, 2)                             AS revenue_mln,

Квиз: что вернёт LAST_VALUE?

last_value(unit_price) OVER (PARTITION BY material_id ORDER BY order_date) — для каждой строки это…

  • последняя цена материала за весь период
  • цена текущей строки (или последней из строк с той же датой)
  • предыдущая цена материала
  • NULL для всех строк, кроме последней

Рамка по умолчанию — RANGE … CURRENT ROW, поэтому «последняя строка рамки» — текущая строка или её последний пир с той же датой. Нужно: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING — или first_value(…) OVER (… ORDER BY order_date DESC).
