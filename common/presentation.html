Почему не Excel: база данных и СУБД

База данных — организованный набор связанных данных. СУБД (система управления БД) — программа, которая хранит данные, проверяет их и выполняет запросы. У нас — PostgreSQL 16 в облаке Yandex.

Строка (запись)

Один объект: один продукт, один заказ, одна партия.

Столбец (атрибут)

Одно свойство с именем и типом. Все значения столбца — одного типа.

Типы данных

integer — целое · numeric(12,2) — деньги · varchar(150) — текст · date — дата · boolean — да/нет

Порядок строк в таблице не гарантирован — если важен порядок, его задают явно (ORDER BY).

Ключи и связи между таблицами

🔑 Первичный ключ (PRIMARY KEY)Уникально определяет строку: не повторяется и не бывает пустым. order_id = 1 — ровно один заказ.
↗ Внешний ключ (FOREIGN KEY)Ссылка на ключ другой таблицы. orders.customer_id хранит номер клиента — СУБД не даст сослаться на несуществующего.

Связь 1:N — «один ко многим»: у одного клиента много заказов, в одном заказе много позиций.

Зачем разносить данные по разным таблицам

Можно было бы хранить продажи одной большой таблицей: в каждой строке заказ, название клиента, его телефон, ИНН, продукт и цена. Но тогда возникают аномалии:

ПроблемаЧто происходит в «одной большой таблице»
Избыточностьтелефон и ИНН клиента повторяются в тысячах строк его заказов
Аномалия обновленияклиент сменил телефон — исправили в одной строке, в остальных остался старый
Аномалия вставкинельзя завести клиента, пока он ничего не заказал
Аномалия удаленияудалили последний заказ — вместе с ним потеряли клиента
Разночтения«ООО Ромашка» и «ООО "РОМАШКА"» — один клиент под двумя именами
Решение — нормализацияКаждый факт хранится один раз в своей таблице (клиенты, заказы, продукты), а таблицы связаны ключами. «Одна большая таблица» (витрина) уместна для отчётов и BI, но не для хранения. В данных «Питание +» дубли клиентов всё-таки есть — их найдём в модуле 2.

Правила записи

  • Запрос заканчивается ;
  • Ключевые слова не зависят от регистра: select = SELECT. Пишем их ПРОПИСНЫМИ — так читается легче
  • Текст — в одинарных кавычках: 'Отменён'
  • Имена столбцов и таблиц — строчными, через _
  • -- комментарий до конца строки, /* … */ — блок
  • SELECT * — все столбцы: только для знакомства с таблицей

AND, OR, NOT и скобки

Задача: отменённые заказы каналов «Маркетплейс» или «Тендер». Приоритет: сначала NOT, потом AND, потом OR.

✘ Без скобок — 59 заказов


SELECT COUNT(*)
FROM   orders
WHERE  status  = 'Отменён'
  AND  channel = 'Маркетплейс'
   OR  channel = 'Тендер';
-- = (Отменён И Маркетплейс) ИЛИ (любой Тендер)

✔ Со скобками — 13 заказов


SELECT COUNT(*)
FROM   orders
WHERE  status = 'Отменён'
  AND  (channel = 'Маркетплейс'
        OR channel = 'Тендер');
-- то же короче: channel IN ('Маркетплейс', 'Тендер')
ПравилоСмешиваете AND и OR — ставьте скобки всегда, даже если «и так работает». Ошибка не выдаёт сообщения: запрос просто возвращает неверную цифру.

NULL — «значение неизвестно»


-- ✘ так НЕ работает: 0 строк
SELECT customer_name FROM customers
WHERE  email = NULL;

-- ✔ так правильно: 21 клиент
SELECT customer_name FROM customers
WHERE  email IS NULL;

-- COUNT(*) — строки, COUNT(столбец) — не-NULL
SELECT COUNT(*)         AS all_rows,
       COUNT(email)     AS with_email,
       COUNT(region_id) AS with_region
FROM   customers;
all_rowswith_emailwith_region
735270

NULL — не ноль и не пустая строка, а отсутствие значения: email не указан, заказ ещё не отгружен (shipped_date), простой не закрыт (end_time).

  • Любое сравнение с NULL даёт UNKNOWN — строка не попадает в результат
  • Проверка — только IS NULL / IS NOT NULL
  • Арифметика с NULL даёт NULL: 100 + NULL → NULL
  • Замена: COALESCE(email, 'нет email')
  • Агрегаты SUM, AVG, COUNT(столбец) пропускают NULL

Создание и изменение данных: DDL и DML


-- DDL: временная таблица — видна только вам
CREATE TEMP TABLE findings (
    finding_id integer      PRIMARY KEY,
    team       char(1)      NOT NULL
                            CHECK (team IN ('А', 'Б')),
    title      varchar(200) NOT NULL,
    loss_rub   numeric(14,2),
    found_on   date NOT NULL DEFAULT CURRENT_DATE
);

-- DML: добавить строки
INSERT INTO findings (finding_id, team, title)
VALUES (1, 'А', 'Скидки сверх политики 10 %'),
       (2, 'Б', 'Повышенный брак на линии 3');


-- изменить значения
UPDATE findings
SET    loss_rub = 1500000
WHERE  finding_id = 1;

-- удалить строки
DELETE FROM findings
WHERE  finding_id = 2;

Разбор: почему у двух аналитиков разные цифры

Два отчёта «Число заказов за 2025 год» дали 2334 и 2201. Оба запроса синтаксически верны.


-- Аналитик 1: 2334
SELECT COUNT(*)
FROM   orders
WHERE  order_date BETWEEN DATE '2025-01-01'
                      AND DATE '2025-12-31';


-- Аналитик 2: 2201
SELECT COUNT(shipped_date)
FROM   orders
WHERE  order_date >= DATE '2025-01-01'
  AND  status <> 'Отменён';
  1. Аналитик 2 исключил отменённые заказы: без них 2240.
  2. COUNT(shipped_date) не считает NULL — 39 неотгруженных заказов выпали, фактически посчитаны отгруженные.
  3. У аналитика 2 нет верхней границы даты — заказы 2026 г. тоже попадут в отчёт, когда появятся.
ВыводУ метрики должно быть определение: «оформлено заказов» и «выполнено заказов» — разные показатели. Запрос метрики хранят и переиспользуют (представления — модуль 9).

Упражнения: переведите вопрос на SQL

Напишите и выполните запрос сами, затем нажимайте «→» — решения появятся по одному.

Команда А Финансы и продажи

  1. Сколько клиентов каждого типа?
    SELECT customer_type, COUNT(*) FROM customers GROUP BY customer_type;
  2. Какие заказы 2025 года не отгружены (без отменённых)?
    … WHERE shipped_date IS NULL AND status <> 'Отменён' AND order_date >= DATE '2025-01-01' — 39
  3. 5 позиций с самой большой скидкой в рублях?
    SELECT order_item_id, quantity * unit_price * discount_pct / 100 AS disc_rub FROM order_items ORDER BY disc_rub DESC LIMIT 5;

Команда Б Производство и закупки

  1. Сколько партий выпущено в каждую смену?
    SELECT shift, COUNT(*) FROM production_batches GROUP BY shift; — день 3135, ночь 2927
  2. Какие простои до сих пор не закрыты?
    SELECT * FROM equipment_downtime WHERE end_time IS NULL; — 4
  3. Название линии и % брака на каждой?
    … FROM production_batches b JOIN production_lines l ON l.line_id = b.line_id GROUP BY l.line_name и 100.0 * SUM(defect_qty) / SUM(produced_qty)
