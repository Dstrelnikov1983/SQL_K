Главная схема курса: логический порядок выполнения запроса


SELECT   c.customer_type,                          -- 6
         date_trunc('month', o.order_date) AS mon, -- 6
         SUM(oi.quantity * oi.unit_price
             * (1 - oi.discount_pct / 100))  AS revenue,
         RANK() OVER (PARTITION BY c.customer_type
                      ORDER BY SUM(oi.quantity * oi.unit_price
                               * (1 - oi.discount_pct / 100)) DESC)
                                             AS rnk -- 5
FROM     pitanie.orders      AS o                   -- 1
JOIN     pitanie.order_items AS oi ON oi.order_id = o.order_id
JOIN     pitanie.customers   AS c  ON c.customer_id = o.customer_id
WHERE    o.status <> 'Отменён'                      -- 2
GROUP BY c.customer_type,
         date_trunc('month', o.order_date)          -- 3
HAVING   COUNT(DISTINCT o.order_id) >= 10           -- 4
ORDER BY c.customer_type, rnk                       -- 8
LIMIT    20;                                        -- 9
  1. 1FROM / JOIN — собрать строки
  2. 2WHERE — отфильтровать строки
  3. 3GROUP BY — сформировать группы
  4. 4HAVING — отфильтровать группы
  5. 5Оконные функции
  6. 6SELECT — выражения, алиасы
  7. 7DISTINCT, затем UNION / EXCEPT…
  8. 8ORDER BY — алиасы уже видны
  9. 9LIMIT / OFFSET / FETCH
Отсюда следуют правилаАлиас из SELECT нельзя в WHERE и HAVING · агрегат нельзя в WHERE · окно нельзя в WHERE и HAVING — только через подзапрос/CTE.
Попросите слушателей до показа пунктов назвать порядок самостоятельно. Статусы заказов в БД: Новый, В работе, Отгружен, Доставлен, Отменён.

М1. Фильтрация и NULL


SELECT customer_name, email, region_id
FROM   pitanie.customers
WHERE  customer_type IN ('Розница', 'HoReCa')
  AND  registration_date >= DATE '2024-01-01'
  AND  registration_date <  DATE '2025-01-01'

Квиз М1: NULL в сортировке

У трёх клиентов не заполнен email. Где они окажутся в результате?


SELECT customer_name, email
FROM   pitanie.customers
ORDER  BY email DESC;
  • В конце списка
  • В начале списка
  • Не попадут в результат
  • Запрос завершится ошибкой

В PostgreSQL NULL при сортировке считается больше любого значения, поэтому при DESC идёт первым. Чтобы убрать их вниз, допишите NULLS LAST. В SQL Server поведение обратное: NULL считается наименьшим.

М2. CASE: две формы


SELECT oi.order_item_id,
       oi.discount_pct,
       CASE
           WHEN oi.discount_pct = 0   THEN 'без скидки'
           WHEN oi.discount_pct <= 10 THEN 'по политике'
           ELSE 'сверх политики'
       END AS discount_band,
       CASE o.channel                    -- простая форма
           WHEN 'Маркетплейс' THEN 'онлайн'
           ELSE 'офлайн'
       END AS channel_group
FROM   pitanie.order_items AS oi
JOIN   pitanie.orders      AS o ON o.order_id = oi.order_id;
  • Ветки проверяются сверху вниз, срабатывает первая TRUE
  • Без ELSE результат — NULL
  • Все ветки должны давать совместимый тип
  • Простая форма CASE x WHEN NULL никогда не сработает — нужна поисковая форма с IS NULL
  • CASE — выражение: можно в SELECT, WHERE, ORDER BY, GROUP BY и внутри агрегатов
СокращенияCOALESCE(a, b, c) — первое не-NULL. NULLIF(a, b) — NULL, если a = b. GREATEST / LEAST игнорируют NULL.

SELECT i.invoice_number,
       i.amount,
       c.customer_name
FROM   pitanie.invoices  AS i
JOIN   pitanie.orders    AS o ON o.order_id    = i.order_id

М3. Главная ловушка: условие в ON или в WHERE


-- A: все клиенты + их заказы за 2025 год
SELECT c.customer_name, COUNT(o.order_id) AS orders_2025
FROM   pitanie.customers AS c
LEFT   JOIN pitanie.orders AS o
       ON  o.customer_id = c.customer_id
       AND o.order_date >= DATE '2025-01-01'
GROUP  BY c.customer_name;
      

-- B: клиенты без заказов в 2025 исчезли!
SELECT c.customer_name, COUNT(o.order_id) AS orders_2025
FROM   pitanie.customers AS c
LEFT   JOIN pitanie.orders AS o
       ON  o.customer_id = c.customer_id
WHERE  o.order_date >= DATE '2025-01-01'
GROUP  BY c.customer_name;
  • Условие на правую таблицу LEFT JOIN в WHERE отбрасывает строки с NULL → LEFT превращается в INNER
  • Условие на левую таблицу в ON не фильтрует левую — её строки сохраняются все
  • Используйте COUNT(o.order_id), а не COUNT(*): иначе клиент без заказов даст 1
Размножение строкСоединение «один ко многим» с двумя дочерними таблицами (позиции + оплаты) умножает строки: суммы завышаются. Агрегируйте каждую ветку отдельно, потом соединяйте.
SELF-JOINemployees e JOIN employees m ON m.employee_id = e.manager_id — сотрудник и его руководитель.

Квиз М3: CROSS JOIN

В production_lines 5 строк, в календаре на январь — 31 день. Сколько строк вернёт запрос?


SELECT l.line_id, d::date AS day
FROM   pitanie.production_lines AS l
CROSS  JOIN generate_series(DATE '2025-01-01',
                            DATE '2025-01-31',

  • 36
  • 155

CROSS JOIN — декартово произведение: 5 × 31 = 155. Такая «сетка» линия × день нужна, чтобы потом LEFT JOIN-ом показать дни без выпуска нулями.

М4. Агрегаты и HAVING


SELECT o.employee_id,
       COUNT(*)                        AS items,
       COUNT(DISTINCT o.order_id)      AS orders,
       ROUND(AVG(oi.discount_pct), 2)  AS avg_disc,
       COUNT(*) FILTER (WHERE oi.discount_pct > 10)
                                       AS over_policy,
       STRING_AGG(DISTINCT o.channel, ', ') AS channels
FROM   pitanie.orders      AS o
JOIN   pitanie.order_items AS oi ON oi.order_id = o.order_id
WHERE  o.order_date >= DATE '2025-01-01'      -- строки
GROUP  BY o.employee_id
HAVING AVG(oi.discount_pct) > 10              -- группы
ORDER  BY avg_disc DESC;
ФункцияКак считает NULL
COUNT(*)все строки
COUNT(col)только не-NULL
COUNT(DISTINCT col)уникальные не-NULL
SUM, AVG, MIN, MAXигнорируют NULL; на пустом наборе → NULL
  • В SELECT — только столбцы из GROUP BY и агрегаты
  • WHERE — до группировки, агрегаты в нём запрещены
  • HAVING — после, по агрегатам
  • FILTER (WHERE …) — условная агрегация вместо SUM(CASE …)
Среднее от процентов ≠ процент от суммДолю брака считайте как SUM(defect) / SUM(produced), а не AVG(defect_pct): «дробь носят в двух карманах».

М4. Итоги: ROLLUP, CUBE, GROUPING SETS


SELECT CASE WHEN GROUPING(shift) = 1
            THEN 'Итого' ELSE shift END        AS shift,
       CASE WHEN GROUPING(line_id) = 1
            THEN 'Все линии'
            ELSE line_id::text END             AS line,
       SUM(defect_qty)                          AS defects
FROM   pitanie.production_batches
GROUP  BY ROLLUP (shift, line_id)
ORDER  BY GROUPING(shift), shift,
          GROUPING(line_id), line_id;
GROUPING(col) = 1, если столбец «свёрнут» в итоговой строке. Отличает итог от настоящего NULL в данных.
КонструкцияНаборы группировкиДля n столбцов
ROLLUP (a, b)(a, b), (a), ()n + 1
CUBE (a, b)(a, b), (a), (b), ()2n
GROUPING SETS ((a), (b))ровно перечисленные—
Как считать строки результатаСложите число групп по каждому набору. 2 смены × 5 линий: ROLLUP = 10 + 2 + 1 = 13; CUBE = 10 + 2 + 5 + 1 = 18.
Порядок в ROLLUP важенROLLUP (shift, line_id) даёт подытоги по сменам, ROLLUP (line_id, shift) — по линиям.

Квиз М4: COUNT и NULL

В таблице 4 строки, значения v: 10, NULL, 20, NULL. Что вернёт запрос?


SELECT COUNT(*), COUNT(v), AVG(v)
FROM   (VALUES (10), (NULL), (20), (NULL)) AS t (v);
  • 4, 4, 7.5
  • 2, 2, 15
  • 4, 2, 15
  • 4, 2, 7.5

COUNT(*) считает строки (4), COUNT(v) — не-NULL значения (2). AVG делит сумму на число не-NULL: 30 / 2 = 15. Если NULL означает «ноль», нужно AVG(COALESCE(v, 0)) = 7.5.

-- партии с браком выше среднего по СВОЕЙ линии (коррелированный подзапрос)
SELECT b.batch_number, b.line_id, b.shift,
       ROUND(100.0 * b.defect_qty / b.produced_qty, 2) AS defect_pct
FROM   pitanie.production_batches AS b
WHERE  1.0 * b.defect_qty / b.produced_qty >
       (SELECT SUM(x.defect_qty)::numeric / SUM(x.produced_qty)
        FROM   pitanie.production_batches AS x

М5. EXISTS против IN: ловушка NULL


-- регионы без дистрибьюторов
-- ✘ у одного дистрибьютора region_id IS NULL → 0 строк
SELECT r.region_name
FROM   pitanie.regions AS r
WHERE  r.region_id NOT IN (
       SELECT c.region_id
       FROM   pitanie.customers AS c
       WHERE  c.customer_type = 'Дистрибьютор');

-- ✔ безопасная форма → 2 региона
SELECT r.region_name
FROM   pitanie.regions AS r
WHERE  NOT EXISTS (
       SELECT 1
       FROM   pitanie.customers AS c
       WHERE  c.customer_type = 'Дистрибьютор'
         AND  c.region_id = r.region_id);
Почему NOT IN ломаетсяx NOT IN (1, NULL) = x <> 1 AND x <> NULL = … AND UNKNOWN → никогда не TRUE.
  • EXISTS — полусоединение (semi join): строка внешнего запроса выводится один раз, даже если совпадений много
  • NOT EXISTS — антисоединение (anti join), NULL не боится
  • В EXPLAIN: Hash Semi Join, Hash Anti Join
  • Что писать в SELECT внутри EXISTS — неважно (SELECT 1)
Подзапрос или JOIN?Нужны столбцы второй таблицы → JOIN. Нужен только факт наличия → EXISTS (нет размножения строк).

Квиз М5: пустой скалярный подзапрос

Клиента с customer_id = 99999 не существует. Что вернёт запрос?


SELECT 'Лимит: ' || COALESCE(
         (SELECT credit_limit::text
          FROM   pitanie.customers
          WHERE  customer_id = 99999),
         'не задан') AS info;
  • Ноль строк
  • Ошибка: подзапрос не вернул строк
  • Лимит: не задан
  • NULL

Скалярный подзапрос, не нашедший строк, возвращает NULL, а не «ноль строк». COALESCE подставляет текст по умолчанию. Ошибкой закончился бы подзапрос, вернувший больше одной строки.

М9. CTE и рекурсия


WITH RECURSIVE org AS (
    -- якорь: с кого начинаем
    SELECT employee_id, full_name, manager_id,
           1 AS lvl,
           full_name::text AS path
    FROM   pitanie.employees
    WHERE  manager_id IS NULL
    UNION ALL
    -- рекурсивная часть: ссылается на org
    SELECT e.employee_id, e.full_name, e.manager_id,
           o.lvl + 1,
           o.path || ' → ' || e.full_name
    FROM   pitanie.employees AS e
    JOIN   org               AS o ON e.manager_id = o.employee_id
)
SELECT lvl, path
FROM   org
ORDER  BY path;

  • Защита от циклов: массив пути или CYCLE … SET … USING (PG 14+)

  • Генерация календаря: generate_series или рекурсивный CTE

М10. Блок, переменные, управление потоком


DO $$
DECLARE
    v_limit   pitanie.customers.credit_limit%TYPE;
    v_cust    pitanie.customers%ROWTYPE;
    v_debt    numeric := 0;
    c_max     CONSTANT numeric := 1.2;
    r         record;
BEGIN
    SELECT * INTO STRICT v_cust
    FROM   pitanie.customers
    WHERE  customer_id = 17;

    v_limit := v_cust.credit_limit;

    FOR r IN SELECT i.invoice_id, i.amount
             FROM   pitanie.invoices AS i
             JOIN   pitanie.orders   AS o ON o.order_id = i.order_id
             WHERE  o.customer_id = v_cust.customer_id
    LOOP
        v_debt := v_debt + r.amount;
        EXIT WHEN v_debt > v_limit * c_max;
    END LOOP;

    IF v_debt > v_limit THEN
        RAISE NOTICE '% : долг % при лимите %',
                     v_cust.customer_name, v_debt, v_limit;
    ELSIF v_debt = 0 THEN
        RAISE NOTICE 'Счетов нет';
    END IF;
END
$$;
  • DO $$ … $$ — анонимный блок; $$ — долларовые кавычки
  • Присваивание :=; %TYPE, %ROWTYPE, record — тип «по образцу»
  • SELECT … INTO: 0 строк → NULL и FOUND = false; много строк → первая
  • INTO STRICT: 0 строк → NO_DATA_FOUND, > 1 → TOO_MANY_ROWS
  • Циклы: LOOP … EXIT WHEN, WHILE, FOR i IN 1..10 (счётчик объявляется неявно), FOR r IN SELECT, FOREACH x IN ARRAY
  • PERFORM — выполнить запрос и отбросить результат
Цикл или запрос?Построчная обработка в цикле почти всегда медленнее одного UPDATE … FROM. Цикл — когда логика действительно пошаговая.

М10. Динамический SQL и ошибки


DO $$
DECLARE
    v_tab text := 'production_batches';
    v_cnt bigint;
    v_msg text;
BEGIN
    EXECUTE format('SELECT COUNT(*) FROM pitanie.%I
                    WHERE line_id = $1', v_tab)
    INTO  v_cnt

    IF v_cnt = 0 THEN
        RAISE EXCEPTION 'Нет партий на линии %', 3

EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'Деление на ноль';
    WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS v_msg = MESSAGE_TEXT;
        RAISE NOTICE 'Ошибка % : %', SQLSTATE, v_msg;
END
$$;

Квиз М11: снимок в REPEATABLE READ

Сессия 1 открыла транзакцию и прочитала остаток (500). Сессия 2 изменила его на 300 и зафиксировала. Что увидит сессия 1 при повторном чтении?


-- Сессия 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT qty FROM stock WHERE material_id = 5;   -- 500
--   ... сессия 2: UPDATE stock SET qty = 300 ...; COMMIT;
SELECT qty FROM stock WHERE material_id = 5;   -- ?
COMMIT;
  • 300
  • 500
  • Ошибка 40001 при чтении
  • Сессия 1 будет ждать снятия блокировки

На REPEATABLE READ транзакция видит снимок, сделанный при первом запросе, поэтому снова прочитает 500. На READ COMMITTED было бы 300. Ошибка 40001 возникла бы, если бы сессия 1 попыталась изменить эту строку.

Квиз М12: COMMIT в функции

Что произойдёт при вызове SELECT f_close_month();, если внутри функции после UPDATE стоит COMMIT?

  • UPDATE зафиксируется, функция продолжит работу
  • Ошибка invalid transaction termination: в функции нельзя управлять транзакцией
  • COMMIT будет проигнорирован
  • Функция зафиксирует транзакцию после возврата результата

Функция выполняется внутри транзакции вызывающего запроса и не может её завершить. Для «закрытия месяца» с фиксацией по шагам нужна PROCEDURE, вызванная через CALL вне явного блока транзакции.

  1. col <> 1 не возвращает NULL — нужен IS DISTINCT FROM
  2. 7 / 2 = 3: целочисленное деление
  3. '12.7'::integer — ошибка; сначала ::numeric
  4. Условие по правой таблице LEFT JOIN в WHERE превращает его в INNER
  5. Соединение с двумя дочерними таблицами размножает строки и завышает суммы
  6. Среднее от процентов ≠ процент от сумм
  1. NOT IN с NULL в подзапросе → пустой результат
  2. Скалярный подзапрос с > 1 строкой — ошибка; с 0 строк — NULL
  3. UNION удаляет дубли и внутри первого набора
  4. Рамка по умолчанию — RANGE с «пирами»; LAST_VALUE = текущая строка
